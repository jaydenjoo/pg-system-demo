## 1. PCI DSS가 뭔가요?

### 한 줄 요약

> "카드 정보를 다루는 회사가 반드시 지켜야 하는 보안 규칙집"

### 쉽게 이해하기

은행 금고를 생각해 보세요. 금고에는 이런 규칙이 있죠:
- 금고 문은 항상 잠겨 있어야 한다
- 열쇠는 지정된 사람만 가질 수 있다
- 누가 금고를 열었는지 기록해야 한다
- 정기적으로 금고 상태를 점검해야 한다

**PCI DSS**는 바로 이 "금고 규칙"의 디지털 버전입니다.
PCI DSS는 "Payment Card Industry Data Security Standard"의 약자로,
Visa, Mastercard 등 카드사들이 만든 국제 보안 표준입니다.

### 왜 지켜야 하나요?

| 질문 | 답변 |
|------|------|
| 안 지키면? | 카드사와의 계약 해지, 과징금, 영업 정지 |
| 법적 책임? | 전자금융거래법 위반 시 **10년 이하 징역 또는 1억 원 이하 벌금** |
| 누가 감사? | 매년 외부 QSA(인증심사기관) 감사 + 금융감독원 검사 |

### PCI DSS 4.0.1 핵심 12가지 요건

비유로 풀어보면 이렇습니다:

| # | PCI DSS 요건 | 비유 |
|---|-------------|------|
| 1 | 네트워크 보안 설치 | 건물 울타리와 출입구 설치 |
| 2 | 안전한 기본 설정 | 현관문 비밀번호를 "1234"에서 바꾸기 |
| 3 | 카드 데이터 보호 | 금고 안에 돈 넣고 잠그기 |
| 4 | 전송 시 암호화 | 현금 수송 시 보안 차량 사용 |
| 5 | 악성코드 방어 | 건물에 방범 카메라 설치 |
| 6 | 안전한 시스템 개발 | 금고를 튼튼한 재료로 만들기 |
| 7 | 접근 제한 | 금고 열쇠를 필요한 사람에게만 |
| 8 | 사용자 식별 | 출입 시 신분증 확인 |
| 9 | 물리적 접근 제한 | 서버실 잠금장치 |
| 10 | 모니터링 & 로깅 | CCTV 24시간 녹화 |
| 11 | 정기 보안 테스트 | 방범 시스템 정기 점검 |
| 12 | 보안 정책 수립 | 보안 규칙집 만들고 교육 (**바로 이 문서!**) |

## 2. 우리 시스템에서 지키는 것들

### 카드 데이터의 여정 — "고객 결제부터 정산까지"

아래는 카드 결제가 이루어질 때 데이터가 어떻게 흐르는지 보여줍니다.

```
고객 (카드번호 입력)
    │
    ▼
┌──────────────────┐
│  가맹점 결제 페이지  │  ← 카드번호가 여기를 거쳐갑니다
│  (HTTPS/TLS 1.3) │     (우리 서버에 카드번호가 저장되지 않습니다!)
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│  토큰화 서버       │  ← 카드번호를 "토큰"으로 바꿉니다
│  (AES-256-GCM)   │     4123-XXXX-XXXX-7890 → tok_a8f3k29d
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│  PG 관리 시스템     │  ← 우리 시스템. 토큰만 저장합니다
│  (우리가 관리)      │     실제 카드번호는 절대 없습니다!
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│  카드사/은행 API    │  ← 실제 결제 승인 처리
└──────────────────┘
```

### 핵심 포인트

**"토큰화"란 뭔가요?**

> 실제 카드번호 대신 의미 없는 대체값(토큰)을 사용하는 기술입니다.

비유하면 이렇습니다:
- 진짜 여권 대신 "여권번호"만 적힌 메모를 가지고 다니는 것
- 메모를 잃어버려도 여권 자체는 안전합니다
- 메모만으로는 본인인증이 불가능합니다

**우리 시스템에서 보호하는 데이터:**

| 데이터 유형 | 보호 방법 | 비유 |
|------------|----------|------|
| 카드번호 (PAN) | 토큰화 — 저장 자체를 안 함 | 금을 보관하지 않고 보관증만 보유 |
| 비밀번호 | bcrypt 해싱 — 원래 값 복원 불가 | 종이를 분쇄기에 넣은 것 |
| 가맹점 정보 | AES-256 암호화 — 키 없으면 못 읽음 | 금고 속 봉투 |
| 통신 데이터 | TLS 1.3 암호화 — 중간에서 못 엿봄 | 보안 수송 차량 |
| 접근 기록 | 감사 로그 — 5년 보관, 위변조 불가 | CCTV 녹화본 봉인 |

### 우리 시스템의 보안 장치 (4개 층)

```
┌─────────────────────────────────────────────┐
│            1층: DMZ (경비실)                   │
│    Nginx + WAF + Rate Limiter               │
│    → 이상한 요청은 여기서 차단                   │
├─────────────────────────────────────────────┤
│            2층: App Zone (사무실)              │
│    NestJS API 서버                           │
│    → 인증(JWT+MFA) 확인, 비즈니스 처리            │
├─────────────────────────────────────────────┤
│            3층: Data Zone (금고)              │
│    PostgreSQL + 암호화 + 토큰화               │
│    → 가장 민감한 데이터 보관                     │
├─────────────────────────────────────────────┤
│            4층: Management (관제실)            │
│    모니터링 + 알림 + 로그                      │
│    → VPN + MFA 없이는 접근 불가                │
└─────────────────────────────────────────────┘
```

## 3. 당신이 지켜야 할 5가지 규칙

### 규칙 1: 카드번호를 눈으로 보거나 메모하지 마세요

**왜?**
카드번호를 메모장에 적거나, 캡처하거나, 메신저로 전달하는 것은
PCI DSS 3.4.1 위반이며, 법적 처벌 대상입니다.

**이런 상황이 생기면:**

| 상황 | 올바른 대응 |
|------|-----------|
| 고객이 전화로 카드번호를 불러줌 | "고객님, 보안을 위해 결제 페이지에서 직접 입력해 주세요" |
| 화면에 카드번호가 보임 | 즉시 보안팀에 신고 (마스킹 처리 안 된 것은 버그!) |
| 동료가 카드번호를 메신저로 보냄 | 즉시 삭제 요청 + 보안팀 보고 |
| 로그 파일에 카드번호가 있음 | 로그 파일 즉시 삭제 + 보안팀 보고 |

> (PCI DSS 요건 3 — 저장된 카드 데이터 보호)

### 규칙 2: 비밀번호 12자 이상 + MFA 반드시 사용

**왜 12자?**
- 8자 비밀번호: 해커가 **1시간** 만에 해독 가능
- 12자 비밀번호: 해커가 **수백 년**이 걸림
- PCI DSS 8.3.6은 12자 이상을 의무로 규정합니다

**좋은 비밀번호 만드는 팁:**

```
나쁜 예시:  password123!    ← 사전에 있는 단어 + 숫자
나쁜 예시:  Company2026!    ← 회사 이름 + 연도
좋은 예시:  naSalmon#Jump7  ← 무관한 단어 조합 + 특수문자 + 숫자
더 좋은:   사과나무달리기37번! ← 한국어도 OK, 기억하기 쉽고 길이가 길면 좋음
```

**MFA(다중 인증)란?**

> "비밀번호 + 내 핸드폰에 뜨는 숫자"를 **둘 다** 입력해야 로그인

비유: 금고를 열려면 (1) 비밀번호 + (2) 지문 둘 다 필요한 것
→ 비밀번호가 유출되어도 핸드폰이 없으면 로그인 불가!

> (PCI DSS 요건 8.4.2 — CDE 접근 시 MFA 필수)

### 규칙 3: 모르는 메일의 링크/첨부파일 열지 마세요

**왜?**
PG사를 노리는 해커의 **80%가 피싱 이메일**로 시작합니다.

**피싱 이메일 구별법:**

| 의심 포인트 | 예시 |
|------------|------|
| 발신자 주소가 이상함 | support@pg-system.com (정상) vs support@pg-systme.com (오타!) |
| "긴급" "즉시 확인" 을 강조 | "계정이 정지됩니다! 지금 클릭하세요" |
| 첨부파일이 .exe, .zip | 정상 업무 메일은 보통 .pdf, .xlsx |
| 링크 URL이 다름 | 마우스를 올리면 실제 URL이 다른 곳으로 향함 |

**이런 메일을 받으면:**
1. 링크/첨부파일 **절대 클릭 금지**
2. 보안팀에 메일 원본 전달 (전달 시 "피싱 의심" 표기)
3. 이미 클릭했다면 → **즉시** 보안팀에 연락, PC 네트워크 분리

> (PCI DSS 요건 5.4.1 — 피싱 방지 메커니즘 구현)

### 규칙 4: 업무용 PC에 개인 프로그램 설치 금지

**왜?**
검증되지 않은 프로그램에 악성코드가 숨어 있을 수 있습니다.
PG 시스템에 접속하는 PC가 감염되면 카드 데이터가 유출될 수 있습니다.

**금지 사항:**
- 토렌트 프로그램 설치
- 출처 불명 유틸리티 설치
- 브라우저 확장 프로그램 무분별 설치
- USB 드라이브 무단 사용

**프로그램이 필요하면:**
- IT팀에 설치 요청 → 승인 후 IT팀이 설치

> (PCI DSS 요건 5 — 악성 소프트웨어로부터 보호)

### 규칙 5: 이상한 것을 보면 즉시 보고

**어떤 게 "이상한 것"인가요?**

| 상황 | 보고 필요? |
|------|----------|
| 내가 로그인 안 했는데 로그인 알림이 왔다 | 즉시 보고 |
| 화면에 평소 안 보이던 데이터가 보인다 | 보고 |
| 시스템이 갑자기 느려졌다 | 보고 |
| 동료가 다른 사람 계정으로 로그인하고 있다 | 보고 |
| 모르는 사람이 서버실에 들어가고 있다 | 즉시 보고 |
| "보안 점검"이라며 비밀번호를 물어보는 전화 | 절대 알려주지 말고 보고 |

**보고 방법:**
1. **긴급** (카드 데이터 유출 의심): 보안팀 직통 전화
2. **일반** (이상 징후): 사내 보안 신고 채널 또는 이메일

**절대 하면 안 되는 것:**
- "별거 아닌 것 같은데..." 하고 넘기기
- 혼자 해결하려고 시도하기
- 나중에 보고하기 (골든타임은 **1시간 이내**)

> (PCI DSS 요건 12.10.1 — 보안 사고 대응 계획)

## 4. 보안 사고 사례

### 사례 1: KCP 개인정보 유출 사건 (2014년)

**무슨 일이?**
- PG사(KCP)의 내부 직원이 고객 개인정보 약 53만 건을 유출
- 이름, 주민등록번호, 카드번호, 유효기간 등 민감 정보 포함

**왜 일어났나?**
- 내부자의 권한 남용 — 업무에 필요한 것 이상의 데이터에 접근 가능
- 접근 로그 모니터링 부재 — 대량 조회를 감지하지 못함
- 최소 권한 원칙 미적용 — 한 사람이 너무 많은 데이터에 접근

**교훈:**
- 직원 누구나 "내부 위협"이 될 수 있음
- 접근 권한은 "업무에 꼭 필요한 만큼만" 부여 (최소 권한 원칙)
- **모든 데이터 접근은 기록**되고 감시된다는 인식이 중요

**우리 시스템의 대응:**
- RBAC(역할 기반 접근 제어) — SuperAdmin/Admin/Manager/Viewer 각각 다른 권한
- 감사 로그 — 누가, 언제, 어떤 데이터를 조회했는지 **5년 보관**
- 해시 체인 — 로그 위변조 불가능 (수정하면 체인이 끊어져 탐지됨)

### 사례 2: 하트랜드(Heartland) 데이터 유출 사건 (2008년, 미국)

**무슨 일이?**
- 미국 5위 PG사, 카드번호 **1억 3천만 건** 유출
- 당시 역대 최대 규모의 데이터 유출 사건

**왜 일어났나?**
- SQL 인젝션 공격 — 해커가 웹사이트 입력란에 악성 코드 삽입
- 카드번호 평문 저장 — 암호화 없이 DB에 그대로 저장
- 네트워크 분리 미흡 — 한 곳이 뚫리자 전체 시스템 접근 가능

**교훈:**
- 입력값 검증 없이는 어떤 시스템도 안전하지 않음
- **카드번호는 절대 평문 저장하면 안 됨** (토큰화 필수)
- 네트워크는 구역별로 분리해야 피해를 최소화

**우리 시스템의 대응:**
- Parameterized Query — SQL 인젝션 원천 차단 (Raw SQL 사용 금지)
- 토큰화 — 카드번호를 저장하지 않고 토큰으로 대체
- 4계층 네트워크 — DMZ/App/Data/Management 분리

### 사례 3: 이니시스 해킹 시도 (2023년, 한국)

**무슨 일이?**
- 국내 주요 PG사인 이니시스의 가맹점 관리 시스템에 대한 해킹 시도 탐지
- 해외 IP에서 관리자 페이지에 대한 대량 로그인 시도 (Credential Stuffing)

**왜 일어났나?**
- 다른 사이트에서 유출된 ID/비밀번호 조합을 돌려가며 시도
- 관리자 페이지가 인터넷에 직접 노출
- 초기에는 Rate Limiting이 미흡

**교훈:**
- 관리자 페이지는 반드시 VPN/IP 제한 뒤에 위치
- MFA가 없으면 비밀번호 유출 시 바로 뚫림
- 비정상 로그인 패턴 감지 → 즉시 차단 시스템 필요

**우리 시스템의 대응:**
- MFA(TOTP) 필수 — 비밀번호만으로 로그인 불가
- 로그인 5회 실패 → 30분 계정 잠금
- Rate Limiting — IP당 분당 10회 제한
- 관리 콘솔은 VPN + MFA 필수

## 5. 확인 퀴즈

### 객관식 (각 10점, 7문항)

**Q1. PCI DSS는 무엇의 약자입니까?**
- (a) Personal Computer Data Security Standard
- (b) Payment Card Industry Data Security Standard
- (c) Private Customer Information Data Safety Standard
- (d) Public Cloud Infrastructure Data Security Standard

**Q2. 우리 시스템에서 카드번호는 어떻게 처리됩니까?**
- (a) 암호화하여 데이터베이스에 저장
- (b) 토큰화하여 토큰만 저장하고 실제 카드번호는 저장하지 않음
- (c) 마스킹 처리하여 데이터베이스에 저장
- (d) 카드번호 뒷 4자리만 저장

**Q3. PCI DSS 4.0.1이 요구하는 최소 비밀번호 길이는?**
- (a) 8자
- (b) 10자
- (c) 12자
- (d) 16자

**Q4. 피싱 이메일을 받았을 때 올바른 대응은?**
- (a) 링크를 클릭해서 진짜인지 확인한다
- (b) 첨부파일을 다운로드해서 바이러스 검사를 한다
- (c) 링크/첨부파일을 열지 않고 보안팀에 원본 전달한다
- (d) 무시하고 삭제한다

**Q5. MFA(다중 인증)가 필요한 이유는?**
- (a) 로그인 속도를 높이기 위해
- (b) 비밀번호가 유출되어도 추가 인증 없이는 접근할 수 없게 하기 위해
- (c) 회사 정책일 뿐 보안과 무관하다
- (d) 개인정보보호법에서만 요구한다

**Q6. 동료가 카드번호를 메신저로 보냈을 때 올바른 대응은?**
- (a) 확인하고 삭제 요청한다
- (b) 즉시 삭제 요청하고 보안팀에 보고한다
- (c) 화면 캡처해서 증거를 남긴다
- (d) 답장으로 "알겠어"라고 한다

**Q7. 보안 사고를 발견했을 때 골든타임은?**
- (a) 24시간 이내
- (b) 업무 시간 내
- (c) 1시간 이내
- (d) 다음 근무일

### 주관식 (각 10점, 3문항)

**Q8. "토큰화"가 무엇인지 본인의 말로 설명하세요.**

(예시 답안: 실제 카드번호 대신 의미 없는 대체값을 사용하여, 데이터가 유출되어도 원래 카드번호를 알 수 없게 하는 보안 기술)

**Q9. 우리 시스템의 보안 4개 층(DMZ, App, Data, Management)이 왜 필요한지 비유를 들어 설명하세요.**

(예시 답안: 은행에 경비실-사무실-금고-관제실이 분리되어 있는 것처럼, 한 곳이 뚫려도 금고(데이터)까지 바로 도달하지 못하게 하기 위해 계층을 분리)

**Q10. 업무 중 "이상한 것"을 발견했을 때 취해야 할 3단계 행동을 적으세요.**

(예시 답안: (1) 현재 상황을 기록, (2) 보안팀에 즉시 보고, (3) 혼자 해결하려 하지 않고 지시를 따름)

## 6. 부록: 보안 용어 사전

### 기본 용어

| 용어 | 뜻 | 비유 |
|------|-----|------|
| **PCI DSS** | 카드 데이터 보안 국제 표준 | 은행 금고의 설계 기준서 |
| **CDE** | 카드 데이터 환경 (Cardholder Data Environment) | 카드번호가 지나가거나 저장되는 모든 구역 |
| **PAN** | Primary Account Number (카드 앞면의 16자리) | 금고 속 금괴 그 자체 |
| **토큰화** | 카드번호를 의미 없는 대체값으로 바꾸는 기술 | 금괴 대신 보관증만 들고 다니기 |
| **MFA** | 다중 인증 (Multi-Factor Authentication) | 금고 열려면 비밀번호 + 지문 둘 다 필요 |
| **TOTP** | 시간 기반 일회용 비밀번호 (핸드폰 앱의 6자리 숫자) | 30초마다 바뀌는 디지털 열쇠 |

### 암호화 용어

| 용어 | 뜻 | 비유 |
|------|-----|------|
| **AES-256-GCM** | 데이터를 암호화하는 알고리즘 (256비트 키) | 세상에서 가장 복잡한 자물쇠 |
| **TLS 1.3** | 인터넷 통신을 암호화하는 프로토콜 | 보안 수송 차량의 장갑 두께 |
| **해싱 (Hashing)** | 데이터를 한 방향으로만 변환 (되돌리기 불가) | 종이를 분쇄기에 넣으면 원본 복원 불가 |
| **bcrypt** | 비밀번호 해싱 알고리즘 | 비밀번호 전용 분쇄기 |
| **KMS** | 암호화 키를 안전하게 관리하는 서비스 | 금고 열쇠를 보관하는 또 다른 금고 |

### 인증/접근 용어

| 용어 | 뜻 | 비유 |
|------|-----|------|
| **JWT** | 로그인 후 받는 인증 토큰 (JSON Web Token) | 건물 출입증 (15분마다 갱신) |
| **RBAC** | 역할 기반 접근 제어 | 부장은 금고까지, 사원은 사무실까지만 |
| **세션** | 로그인 ~ 로그아웃 사이의 연결 상태 | 건물에 들어온 순간 ~ 나가는 순간 |
| **Rate Limiting** | 일정 시간 내 요청 횟수 제한 | 1분에 문 열기 시도 10번까지만 허용 |

### 공격 용어

| 용어 | 뜻 | 비유 |
|------|-----|------|
| **피싱** | 가짜 메일/사이트로 정보를 빼내는 공격 | "은행인 척" 전화해서 비밀번호 물어보기 |
| **SQL 인젝션** | 입력란에 악성 코드를 넣어 DB를 조작 | 출입신청서에 "모든 문 열어라"라고 적기 |
| **XSS** | 웹페이지에 악성 스크립트를 삽입하는 공격 | 게시판에 함정을 설치하는 것 |
| **DDoS** | 대량의 가짜 요청으로 서비스를 마비시킴 | 가게 앞에 수천 명이 줄 서서 진짜 손님 못 들어오게 |
| **Credential Stuffing** | 유출된 ID/PW 조합을 돌려가며 로그인 시도 | 다른 집 열쇠를 우리 집 문에 하나씩 끼워보기 |

### 법규 용어

| 용어 | 뜻 | 비유 |
|------|-----|------|
| **전자금융거래법** | 전자금융(PG, 간편결제 등) 규율 법률 | PG 업계의 헌법 |
| **전자금융감독규정** | 금융감독원의 세부 규정 | PG 업계의 시행령 |
| **개인정보보호법** | 개인정보 수집·이용·보관 규율 | 개인 신상 정보 취급 규칙 |
| **QSA** | PCI DSS 인증 심사관 (Qualified Security Assessor) | 은행 금고 검사관 |
| **KISA** | 한국인터넷진흥원 — 보안 사고 신고 기관 | 사이버 119 |
