## 1. 시스템 전체 그림

### "자판기"로 이해하는 PG 관리시스템

우리 시스템을 "자판기"에 비유하면 쉽게 이해할 수 있습니다.

```
                              우리 시스템
                    ┌─────────────────────────┐
 고객 (동전 투입)      │                         │
      │             │   ┌─────────────────┐   │
      ▼             │   │  Nginx (투입구)   │   │      카드사/은행
 ┌──────────┐       │   │  - 동전 크기 확인  │   │    ┌──────────┐
 │ 가맹점    │ ──────┼──▶│  - 위조 동전 거부  │   │───▶│ 실제 결제 │
 │ (자판기)  │       │   └────────┬────────┘   │    │  처리     │
 └──────────┘       │            │             │    └──────────┘
                    │            ▼             │
                    │   ┌─────────────────┐   │
                    │   │  API 서버 (내부)   │   │
                    │   │  - 결제 처리       │   │
                    │   │  - 정산 계산       │   │
                    │   │  - 수수료 정산      │   │
                    │   └────────┬────────┘   │
                    │            │             │
                    │            ▼             │
                    │   ┌─────────────────┐   │
                    │   │  DB (금고)        │   │
                    │   │  - 거래 기록       │   │
                    │   │  - 가맹점 정보      │   │
                    │   │  - 정산 내역       │   │
                    │   └─────────────────┘   │
                    └─────────────────────────┘
```

### 핵심 구성요소 4가지

| 구성요소 | 역할 | 비유 | 접근 포트 |
|---------|------|------|----------|
| **Nginx** | 외부 요청을 받아 필터링 후 API로 전달 | 자판기 투입구 (크기 맞는 동전만 통과) | 80/443 |
| **API 서버** | 비즈니스 로직 처리 (결제, 정산, 인증) | 자판기 내부 기계 (동전 분류 → 음료 배출) | 4000 |
| **PostgreSQL** | 모든 데이터 저장 (암호화) | 금고 (기록 보관) | 5432 |
| **모니터링** | 시스템 상태 실시간 감시 | 자판기 관리 화면 (고장 시 알림) | 9090/3001 |

### 3개 모듈 (누가 쓰나?)

| 모듈 | 사용자 | 주요 기능 |
|------|--------|----------|
| **관리자 모듈** | PG사 직원 (우리) | 가맹점/대리점 관리, 정산 실행, 수수료 정책, 감사 로그 |
| **가맹점 모듈** | 가맹점 사장님 | 매출 조회, 정산 확인, API 키 관리, 수수료 내역 |
| **대리점 모듈** | 대리점 영업자 | 하위 가맹점 관리, 수수료 정산, 실적 조회 |

### 권한 구조

```
관리자 (우리)                    가맹점               대리점
├── SuperAdmin (전체 권한)       ├── Owner (전체)     ├── Owner (전체)
├── Admin (대부분 권한)          └── Staff (조회만)   └── Staff (조회만)
├── Manager (일부 제한)
└── Viewer (조회만)
```

> **중요**: SuperAdmin만 할 수 있는 것들:
> - 수수료율 변경
> - 계정 생성/삭제
> - 시스템 설정 변경
> - 감사 로그 원본 조회

## 2. 매일 해야 할 일

### 일일 운영 타임라인

아침 출근부터 퇴근까지, 시간대별로 해야 할 일입니다.

#### 09:00 — 시스템 상태 확인

**확인 방법:**
```
GET /api/v1/health
```
또는 Grafana 대시보드의 "System Health" 패널 확인

**정상 응답 예시:**
```json
{
  "status": "ok",
  "info": {
    "database": { "status": "up" },
    "memory": { "status": "up" },
    "disk": { "status": "up" }
  }
}
```

**확인 체크리스트:**

| # | 항목 | 정상 기준 | 이상 시 대응 |
|---|------|----------|------------|
| 1 | 헬스체크 상태 | `"status": "ok"` | `"status": "error"` → 장애 대응 Runbook 참조 |
| 2 | DB 연결 | `"database": "up"` | "down" → DBA 또는 인프라팀 연락 |
| 3 | 메모리 사용률 | < 80% | > 80% → 서비스 재시작 검토 |
| 4 | 디스크 사용률 | < 85% | > 85% → 로그 정리 또는 증설 |
| 5 | 컨테이너 상태 | 4개 모두 running | 1개라도 down → 즉시 복구 |

**컨테이너 상태 확인 명령어:**
```bash
docker compose ps
```

**정상이면 4개 서비스가 모두 "running":**
```
NAME        STATUS         PORTS
nginx       Up (healthy)   80->80, 443->443
api         Up (healthy)   4000->4000
postgres    Up (healthy)   5432->5432
web         Up (healthy)   3000->3000
```

#### 09:15 — 감사 로그 확인

**왜 확인하나요?**
밤사이 비정상적인 접근이 있었는지 확인합니다.
PCI DSS 10.4.1은 최소 1일 1회 로그 검토를 요구합니다.

**확인 포인트:**

| # | 확인 항목 | 비정상 기준 | 대응 |
|---|----------|-----------|------|
| 1 | 로그인 실패 5회 이상 계정 | 3개 이상 계정에서 발생 | 해당 IP 차단 검토, 보안팀 보고 |
| 2 | 심야(00:00~06:00) 로그인 | 야간 근무자 아닌 계정 | 해당 사용자 확인 |
| 3 | 대량 데이터 조회 | 한 계정이 1000건 이상 조회 | 업무 목적 확인, 비정상 시 보고 |
| 4 | 권한 변경 이력 | 승인 없는 변경 | 즉시 보안팀 보고 |
| 5 | Risk Alert | CRITICAL/HIGH 알림 존재 | 장애 대응 Runbook에 따라 처리 |

**감사 로그 해시 체인 검증:**

감사 로그는 "해시 체인"으로 보호됩니다. 비유하면:
- 각 로그 항목이 이전 항목과 "디지털 실"로 연결됨
- 누군가 중간 로그를 수정하면 "실이 끊어져서" 즉시 탐지됨

```bash
# 해시 체인 무결성 검증 (매일 1회)
curl -X POST /api/v1/security/audit-logs/verify-chain \
  -H "Authorization: Bearer $TOKEN"
```

**응답이 `{ verified: false }` 이면 → 즉시 보안팀 보고 (P0 사고)**

#### 09:30 — 백업 성공 여부 확인

**확인 방법:**

```bash
# 오늘 백업 파일 존재 확인
ls -la /backups/daily/ | head -5

# 최근 백업 로그 확인
cat /backups/logs/backup_$(date +%Y%m%d).log
```

**확인 체크리스트:**

| # | 항목 | 정상 기준 | 이상 시 |
|---|------|----------|--------|
| 1 | 백업 파일 존재 | 오늘 날짜 파일 있음 | 수동 백업 실행 |
| 2 | 파일 크기 | 이전 백업 대비 ±20% 이내 | 크기 급변 시 원인 조사 |
| 3 | 체크섬 파일 | .sha256 파일 함께 존재 | 없으면 수동 생성 |
| 4 | 로그에 "SUCCESS" | 마지막 줄에 성공 표시 | "FAILED" 시 즉시 재실행 |

#### 10:00 — 정산 결과 확인

**일일 정산 흐름 이해하기:**

```
어제 거래       오늘 아침          정산 확인
─────────────────────────────────────────
카드 승인 발생 → 정산 자동 계산 → 금액 확인 → 송금 실행
              (CALCULATED)     (CONFIRMED)  (COMPLETED)
```

**확인 포인트:**

| # | 항목 | 정상 기준 | 이상 시 |
|---|------|----------|--------|
| 1 | 정산 건수 | 전일 승인 건수와 일치 | 불일치 시 미매칭 거래 조사 |
| 2 | 정산 금액 | 합산 금액이 입금액과 일치 | 차액 발생 시 정산 운영 Runbook 참조 |
| 3 | 수수료 계산 | 수수료율 × 거래금액 | 오차 시 수수료 설정 확인 |
| 4 | 상태 | 모두 CONFIRMED 또는 COMPLETED | CALCULATED 상태가 남아있으면 확인 필요 |

**수수료 계층 구조 (반드시 이해할 것):**

```
PG 마진 ≤ 대리점 수수료 ≤ 가맹점 수수료

예시: 가맹점 수수료 2.5% → 대리점 수수료 2.0% → PG 마진 1.5%
     (고객이 내는 것)   (대리점 가져가는 것)  (우리가 가져가는 것)

이 순서가 역전되면 → 시스템이 자동 차단 (에러코드 STL_003)
```

## 3. 대시보드 보는 법

### Grafana 접속

- **URL**: `http://localhost:3001` (로컬) 또는 운영 URL
- **로그인**: 운영팀 공유 계정 (최초 접속 시 비밀번호 변경)

### Row 1: 트래픽 현황

#### 요청량 (Requests per Second)

```
평상시 ────────────────── 높음 ──────────── 위험
 0~50 rps                100 rps          500+ rps
   ✅ 정상                ⚠️ 주의          🚨 DDoS 의심
```

| 상태 | 의미 | 대응 |
|------|------|------|
| 0~50 rps | 정상 트래픽 | 없음 |
| 50~100 rps | 트래픽 증가 (프로모션 등) | 모니터링 강화 |
| 100~500 rps | 비정상 증가 | 원인 파악 (이벤트? 공격?) |
| 500+ rps | DDoS 의심 | WAF 규칙 확인, 인프라팀 연락 |

#### 에러율 (Error Rate)

```
정상 ──────────────── 주의 ──────────── 위험
  < 1%               1~5%              > 5%
   ✅                 ⚠️                🚨
```

| 상태 | 의미 | 대응 |
|------|------|------|
| < 1% | 정상 (간헐적 타임아웃 등) | 없음 |
| 1~5% | 일부 기능 장애 가능 | 어떤 API에서 에러 나는지 확인 |
| 5~10% | 서비스 품질 저하 | P2 장애로 분류, 원인 조사 |
| > 10% | 심각한 장애 | P1/P0 장애, 장애 대응 Runbook 즉시 참조 |

#### 응답시간 (Response Time)

```
빠름 ──────────────── 느림 ──────────── 위험
  < 200ms            200~1000ms        > 1000ms
   ✅                 ⚠️                🚨
```

| 상태 | 사용자 체감 | 대응 |
|------|-----------|------|
| < 200ms | 빠름, 불편 없음 | 없음 |
| 200~500ms | 약간 느림 | DB 쿼리 확인 |
| 500~1000ms | 체감 가능한 지연 | DB 커넥션 풀, 느린 쿼리 확인 |
| > 1000ms | 결제 시간 초과 가능 | 즉시 원인 조사 (DB? 네트워크? 외부API?) |

### Row 2: 시스템 리소스

#### CPU 사용률

| 상태 | 대응 |
|------|------|
| < 60% | 정상 |
| 60~80% | 모니터링 강화, 부하 원인 확인 |
| > 80% | 서비스 스케일아웃 또는 불필요 프로세스 종료 |

#### 메모리 사용률

| 상태 | 대응 |
|------|------|
| < 70% | 정상 |
| 70~85% | 메모리 리크 여부 확인 |
| > 85% | 서비스 재시작 검토 + 메모리 증설 요청 |

#### DB 커넥션 수

| 상태 | 대응 |
|------|------|
| < 50% (풀 대비) | 정상 |
| 50~80% | 느린 쿼리 확인, 커넥션 반환 누수 조사 |
| > 80% | 긴급 — 새 요청 거부 가능. 즉시 DBA 연락 |

### Row 3: 보안 & 정산

#### Risk Alert 카운터

| 수준 | 색상 | 의미 |
|------|------|------|
| CRITICAL | 빨강 | 즉시 대응 필요 (카드 데이터 관련 의심) |
| HIGH | 주황 | 15분 이내 확인 필요 |
| MEDIUM | 노랑 | 업무 시간 내 확인 |
| LOW | 파랑 | 참고 사항 |
| INFO | 회색 | 정보성 (대응 불필요) |

#### Health Status

| 표시 | 의미 |
|------|------|
| 초록 (UP) | 모든 서비스 정상 |
| 노랑 (DEGRADED) | 일부 서비스 문제 (DB 느림 등) |
| 빨강 (DOWN) | 서비스 중단 — 즉시 장애 대응 |

## 4. 알림이 왔을 때

### Slack 알림 구조

알림은 아래와 같은 형식으로 Slack에 도착합니다:

```
┌─────────────────────────────────────────┐
│ 🔴 CRITICAL — DB Connection Pool 고갈     │
│                                         │
│ 메시지: Active connections exceeded 80%  │
│         of pool limit (80/100)          │
│ 시간: 2026-03-01 14:32:15 KST           │
│ 서비스: api-server                       │
│                                         │
│ 📋 metadata:                            │
│   active_connections: 80                │
│   pool_limit: 100                       │
│   oldest_query: 45s                     │
└─────────────────────────────────────────┘
```

### 심각도별 대응 플로우

#### CRITICAL (빨간색) — "지금 당장!"

```
알림 수신
  │
  ├─ 1분 이내: 알림 확인, 현상 파악
  │
  ├─ 5분 이내: 장애 대응 Runbook 참조하여 1차 조치
  │            → docs/ops/runbook-incident-response.md
  │
  ├─ 15분 이내: 1차 조치 결과 확인
  │             해결 안 되면 → 에스컬레이션 (팀장/CTO)
  │
  └─ 30분 이내: 상황 보고 (임시 해결/진행 중/해결 완료)
```

**CRITICAL 알림 종류와 즉시 대응:**

| 알림 | 의미 | 즉시 할 일 |
|------|------|----------|
| DB Connection Pool 고갈 | DB 연결 포화 | 느린 쿼리 킬 → API 재시작 |
| API Server DOWN | API 무응답 | 컨테이너 로그 확인 → 재시작 |
| Payment Processing Delay | 결제 처리 지연 | 외부 API(카드사) 상태 확인 |
| Audit Hash Chain Break | 감사 로그 위변조 감지 | 즉시 보안팀 보고 (P0 사고) |
| TLS Certificate Expiring | 인증서 만료 임박 | 즉시 갱신 (만료 시 HTTPS 불가) |

#### HIGH (주황색) — "15분 이내 확인"

```
알림 수신
  │
  ├─ 15분 이내: 현상 확인 및 원인 파악
  │
  ├─ 1시간 이내: 조치 완료 또는 플랜 수립
  │
  └─ 당일 중: 근본 원인 분석 및 재발 방지
```

**HIGH 알림 종류:**

| 알림 | 의미 | 할 일 |
|------|------|------|
| Memory Usage > 80% | 메모리 부족 임박 | 메모리 리크 확인, 재시작 검토 |
| Disk Usage > 85% | 디스크 공간 부족 | 로그 파일 정리, 오래된 백업 삭제 |
| Multiple Login Failures | 계정 공격 의심 | 해당 IP/계정 확인, 차단 검토 |
| FIM Alert | 시스템 파일 변경 감지 | 정상 변경(배포)인지 확인 |
| Settlement Mismatch | 정산 불일치 발견 | 정산 운영 Runbook 참조 |

#### MEDIUM (노란색) — "업무 시간 내 확인"

```
알림 수신
  │
  ├─ 4시간 이내: 현상 확인
  │
  └─ 당일 중: 원인 파악 및 조치
```

| 알림 | 의미 | 할 일 |
|------|------|------|
| Error Rate > 1% | 에러율 증가 | 어떤 API에서 에러 나는지 확인 |
| Response Time > 500ms | 응답 느림 | 느린 쿼리 또는 외부 API 확인 |
| Backup Verification Warning | 백업 검증 경고 | 백업 상태 수동 확인 |

#### LOW / INFO (파란색/회색) — "참고"

- 정기 보고, 시스템 상태 요약 등
- 즉각 대응 불필요, 트렌드 모니터링 목적

### 이메일 알림

- CRITICAL/HIGH 알림은 이메일로도 동시 발송됩니다
- Slack을 확인 못 하는 상황에 대한 백업 채널
- 이메일 설정: `ALERT_EMAIL_TO` 환경변수에 등록된 주소

### 알림 중복 방지

같은 알림이 5분 이내에 반복 발생하면 **자동으로 차단**됩니다.
- 첫 번째 알림만 전달되고, 이후 동일 알림은 무시
- 5분 후 같은 상황이 계속되면 다시 알림 발송
- 이유: 알림 폭탄 방지 (장애 시 수백 개 알림이 쏟아지는 것 방지)

## 5. 자주 묻는 질문 (FAQ)

### Q1. 시스템이 갑자기 느려졌어요. 어떻게 하나요?

**Step 1: 어디가 느린지 확인**
```
Grafana → Row 1 → Response Time 패널
- API 전체가 느림 → Step 2로
- 특정 API만 느림 → 해당 API의 DB 쿼리 확인
```

**Step 2: 리소스 확인**
```
Grafana → Row 2
- CPU > 80% → 불필요 프로세스 확인
- Memory > 85% → 서비스 재시작 고려
- DB Connection > 80% → DBA 연락
```

**Step 3: 외부 요인 확인**
- 카드사/은행 API 응답 지연? → 카드사 상태 페이지 확인
- 트래픽 급증? → Row 1 요청량 확인 (DDoS 가능성)

### Q2. "정산 불일치" 알림이 왔어요. 무엇을 확인하나요?

**정산 불일치 = 입금액과 정산 계산액이 다른 상황**

1. 정산 운영 Runbook 참조 → `docs/ops/runbook-settlement-ops.md`
2. 불일치 유형 확인:
   - **금액 차이**: 수수료 계산 오류 가능성 → 수수료율 설정 확인
   - **건수 차이**: 미매칭 거래 존재 → 대사(Reconciliation) 재실행
   - **상태 차이**: CALCULATED에서 멈춤 → 수동 CONFIRM 필요 여부 확인
3. 차액이 소액(1원 단위)이면 반올림 차이일 수 있음 → 기록 후 모니터링
4. 차액이 클 경우 → 정산팀장에게 보고

### Q3. 백업이 실패했다고 알림이 왔어요.

1. 백업 로그 확인:
   ```bash
   cat /backups/logs/backup_$(date +%Y%m%d).log
   ```
2. 일반적인 원인:
   - **디스크 공간 부족** → 오래된 백업 삭제 후 재실행
   - **DB 연결 실패** → DB 상태 확인
   - **암호화 키 미설정** → 환경변수 BACKUP_ENCRYPTION_KEY 확인
3. 수동 백업 실행:
   ```bash
   ./scripts/backup-database.sh
   ```
4. 성공 후 검증:
   ```bash
   ./scripts/backup-verify.sh
   ```

### Q4. 고객이 "결제가 안 돼요"라고 연락했어요.

**단계별 확인:**

| 순서 | 확인 사항 | 방법 |
|------|----------|------|
| 1 | 시스템 상태 | `GET /api/v1/health` → "ok"인지 확인 |
| 2 | 해당 가맹점 상태 | 가맹점 모듈에서 상태가 ACTIVE인지 확인 |
| 3 | API 에러 로그 | 해당 시간대 에러 로그에 결제 실패 내역 확인 |
| 4 | 카드사 상태 | 특정 카드사 API 응답 지연/실패 여부 |
| 5 | Rate Limit | 해당 가맹점이 요청 제한에 걸렸는지 확인 |

**고객 응대 예시:**
- 시스템 장애인 경우: "현재 일시적인 시스템 점검 중입니다. 잠시 후 다시 시도해 주세요."
- 가맹점 문제인 경우: "가맹점측 설정 확인이 필요합니다. 담당자에게 안내드리겠습니다."
- 카드사 문제인 경우: "해당 카드사 측 일시적 지연이 발생했습니다. 다른 카드로 시도해 주세요."

### Q5. 새로운 가맹점을 등록하려면?

1. **필요 서류 확인**: 사업자등록증, 통장 사본, 대표자 신분증
2. **관리자 모듈** → 가맹점 관리 → 신규 등록
3. **수수료 설정**: 대리점 수수료 ≥ PG 마진 확인 (역전 시 등록 불가)
4. **API 키 발급**: 가맹점에 전달 (이메일 금지 → 안전한 채널 사용)
5. **테스트 거래**: 가맹점 측에서 테스트 결제 진행 확인

### Q6. 수수료율을 변경하려면?

1. **SuperAdmin 권한** 필요 (일반 Admin 불가)
2. 수수료 계층 확인:
   ```
   PG 마진 ≤ 대리점 수수료 ≤ 가맹점 수수료
   ```
   이 규칙을 위반하는 변경은 시스템이 자동 차단 (STL_003)
3. 변경 시 **기존 수수료는 만료 처리**되고 **새 수수료가 생성** (이력 보존)
4. 변경 후 감사 로그에 자동 기록됨

### Q7. 컨테이너가 하나 죽었어요 (Unhealthy).

```bash
# 1. 어떤 컨테이너인지 확인
docker compose ps

# 2. 로그 확인
docker compose logs --tail=50 [서비스명]

# 3. 재시작
docker compose restart [서비스명]

# 4. 재시작 후 상태 확인
docker compose ps
```

**주의:**
- DB(postgres) 컨테이너 재시작 시 진행 중인 정산에 영향 줄 수 있음 → 정산 시간 외 재시작 권장
- 재시작 후에도 반복 실패 → 로그 분석 후 인프라팀 에스컬레이션

### Q8. 감사 로그 해시 체인 검증이 실패했어요.

**이것은 P0 (최고 심각도) 사고입니다.**

의미: 감사 로그가 위변조되었을 가능성

1. **즉시** 보안팀에 보고
2. **절대** 혼자 해결하려 하지 말 것
3. 영향 범위 파악은 보안팀이 수행
4. 보안 절차 Runbook 참조 → `docs/ops/runbook-security-procedures.md`

### Q9. 야간에 알림이 왔는데 CRITICAL이에요. 어떻게 하나요?

1. CRITICAL은 **시간대 무관** 즉시 대응
2. On-call 담당자에게 전화 (Slack DM으로 응답 없으면 전화)
3. 장애 대응 Runbook에 따라 1차 조치
4. 해결 어려우면 CTO 에스컬레이션
5. 조치 후 다음 날 아침 팀 전체 공유

### Q10. "FIM Alert"가 왔어요. 이게 뭔가요?

**FIM = File Integrity Monitoring (파일 무결성 모니터링)**

시스템의 핵심 파일(설정파일, 실행파일 등)이 변경되었는지 감시하는 기능입니다.

**정상 FIM 알림 원인:**
- 정기 배포 직후 → 배포자 확인 후 베이스라인 업데이트
- 보안 패치 적용 후 → 패치 기록 확인

**비정상 FIM 알림 원인:**
- 예정에 없는 파일 변경 → 보안팀 보고
- 알 수 없는 파일 추가 → 즉시 보안팀 보고

**대응:**
```
FIM 알림 → 변경 내용 확인 → 배포/패치 이력과 대조
  → 일치하면: 베이스라인 업데이트
  → 불일치하면: 보안팀 즉시 보고 (P1 사고)
```

### Q11. 월말 정산 보고서는 어떻게 뽑나요?

1. 정산 운영 Runbook → "월간 보고서" 섹션 참조
2. 필요 데이터:
   - 월간 거래 건수/금액 합계
   - 가맹점별 정산 합계
   - 대리점별 수수료 합계
   - 미정산/분쟁 건수
3. SQL 쿼리 모음: `docs/ops/runbook-settlement-ops.md` → "SQL 쿼리 모음" 섹션

### Q12. 시스템 업데이트(배포)는 어떻게 진행하나요?

1. **배포 일정**: 사전 공지 (최소 24시간 전)
2. **점검 시간대**: 새벽 02:00~04:00 (트래픽 최저)
3. **배포 전**:
   - 백업 실행 확인
   - 스테이징 환경 테스트 완료
4. **배포 중**:
   - 롤링 업데이트 (무중단)
   - 헬스체크 모니터링
5. **배포 후**:
   - 전체 서비스 헬스체크
   - FIM 베이스라인 업데이트
   - 테스트 거래 실행
   - 이상 없으면 배포 완료 공지
