## 1. 러버덕이 뭔가요?

러버덕 디버깅은 1999년 "The Pragmatic Programmer" 책에서 시작된 기법이다.
개발자가 고무 오리 인형에게 코드를 한 줄씩 설명하면, 그 과정에서 스스로 문제를 발견하게 된다.

**바이브코딩에서의 의미:**
- 전통적 러버덕 = 개발자가 오리에게 코드를 설명 → 버그 발견
- AI 러버덕 = 바이브 아키텍트가 AI에게 의도를 설명 → AI가 되물으며 모호함 제거 → 정확한 결과물

**비유:** 식당 사장이 신입 요리사에게 "매운 파스타"를 만들라고 했는데,
"얼마나 매운? 어떤 파스타면? 소스 베이스는?"을 안 정해주면 엉뚱한 요리가 나온다.
러버덕 프로토콜은 이 질문들을 미리 정리하는 과정이다.

## 2. 왜 2026년에 더 중요한가?

### 엔지니어링 현실 (2026 Engineering Reality Report)
- 엔지니어 72%가 과도한 업무로 신규 기능 개발 시간 부족
- 실제 코드 작성에 투입하는 시간은 주간 업무의 단 16%
- AI 생성 코드의 약 45%에 보안 취약점 존재 가능
- AI 도입 후 코드 변경 빈도 41% 증가, 배포 안정성 7.2% 감소

### 바이브코딩에 주는 시사점
- AI가 코드를 대신 짜주는 시대 → "무엇을 만들지" 정의하는 능력이 핵심
- 모호한 지시 = 할루시네이션(거짓 답변) + 스파게티 코드의 원인
- 러버덕 프로토콜로 지시를 정제하면 → AI 결과물 품질 극적 향상

## 3. AI 러버덕 vs 전통 러버덕

| 구분 | 전통적 러버덕 | AI 러버덕 (2026) |
|------|-------------|-----------------|
| **역할** | 수동적 리스너 (듣기만 함) | 자율적 에이전트 (되물어보고 실행) |
| **작업 범위** | 단순 논리 확인 | 다단계 계획 수립 + 자율 실행 |
| **기술 기반** | 사람의 지식에 의존 | MCP, Agent2Agent, 벡터DB 기반 맥락 이해 |
| **핵심 가치** | 사고의 외현화 | 사고의 오케스트레이션 + 워크플로우 위임 |

## 4. 바이브코딩 러버덕 4단계 (실전 프로토콜)

### Step 1: 🎯 의도 선언 (Vibe Declaration)
AI에게 작업을 지시하기 전, 먼저 스스로에게 설명한다:
```
나는 [누구를 위해] [무엇을] 만들려고 한다.
왜냐하면 [이런 문제]를 해결하기 위해서다.
성공하면 [이런 결과]가 나와야 한다.
```

**예시:**
```
나는 [PG사 가맹점]을 위해 [AI 상담 에이전트]를 만들려고 한다.
왜냐하면 [반복 문의 처리 비용]을 줄이기 위해서다.
성공하면 [로그인/비로그인에 따라 다른 답변]이 나와야 한다.
```

### Step 2: 🔍 맥락 체크 (Context Audit)
황금공식으로 빠진 정보가 없는지 점검:
- **배경(Background):** 왜 이걸 하는가? 현재 상황은?
- **원하는 결과(Desired Result):** 구체적으로 뭐가 나와야 하나?
- **제약조건(Constraints):** 예산, 기술스택, 기간, 금지사항?
- **출력 형식(Output Format):** 어떤 형태로 받고 싶은가?

### Step 3: 🤖 AI에게 먼저 질문시키기 (Ask-Me-First)
```
"이 작업을 시작하기 전에, 내가 빠뜨린 정보가 있으면 먼저 질문해줘.
최소 3가지 질문을 하고, 내 답변을 받은 후에 작업을 시작해."
```

**왜 중요한가:**
- AI가 바로 답변하면 → 정보 누락으로 잘못된 결과물 확률 높음
- AI가 먼저 질문하면 → 모호한 부분이 명확해지고 → 정확도 급상승
- 비유: 의사가 진단 전에 문진표를 먼저 작성시키는 것과 같다

### Step 4: ✅ 자기 일관성 검증 (Self-Consistency Check)
복잡한 설계나 중요한 결정일 때:
```
"이 문제를 3가지 다른 접근법으로 해결해줘.
각각의 장단점을 비교하고, 가장 적합한 방법을 추천해."
```
→ 3~5가지 방식 중 가장 빈번하게 나오는 결과 = 가장 신뢰할 수 있는 답

## 5. Bounded Autonomy (AI 자율성 한계 설정)

AI에게 자유를 줄수록 위험도 커진다. 반드시 운영 한계를 설정해야 한다.

### AI 자율성 3단계 모델

| 단계 | 이름 | AI 권한 | 사람 역할 | 적용 시점 |
|------|------|---------|----------|----------|
| 1단계 | 제안만 (Suggest-Only) | 초안만 생성 | 모든 실행을 사람이 결정 | 새 프로젝트 시작, 신뢰 구축 전 |
| 2단계 | 승인 후 실행 (Execute-with-Approval) | 작업 후 승인 대기 | 원클릭 승인/거부 | 패턴이 검증된 반복 작업 |
| 3단계 | 가드레일 자율 (Guardrail-Driven) | 정해진 범위 내 자동 실행 | 예외 시에만 개입 | 충분한 실적 데이터 확보 후 |

### 킬 스위치 (Kill Switch) 규칙
- 같은 에러 3회 반복 → AI 자동 중지, 사람에게 보고
- 비용 임계치 초과 → 즉시 중지 + 알림
- 인증/결제/보안 관련 → 항상 사람 승인 필수 (절대 자동 불가)
- 10개 파일 동시 수정 → 금지 (Ralph Loop 안전 규칙과 동일)
- 대규모 리팩토링 → 금지. 막히면 문서화 후 DONE 탈출

### 비유로 이해하기
```
1단계 = 신입 요리사: 레시피 초안만 짜고, 사장이 OK하면 요리 시작
2단계 = 경력 요리사: 요리를 만들어두고 "이거 내볼까요?" 확인받기
3단계 = 베테랑 요리사: 단골 메뉴는 알아서 만들고, 새 메뉴만 확인
```

## 6. 프로젝트별 러버덕 적용 예시

### AI 상담 에이전트 (PG사 프로젝트)
```
러버덕 질문: "가맹점이 '수수료 얼마예요?'라고 물으면 어떻게 되지?"
→ 로그인 상태: "관리자 페이지 > 계약정보에서 확인" 안내
→ 비로그인 상태: "업종/거래규모에 따라 다릅니다" + 영업팀 연결
→ 이 분기를 안 정해두면 AI가 수수료율을 지어내서 말할 수 있다!
```

### AutoVox Flow (시니어 유튜브 자동화)
```
러버덕 질문: "스크립트 생성 → 음성 변환 사이에 뭐가 빠져있지?"
→ 스크립트 품질 검증 단계가 없다!
→ AI가 만든 스크립트를 바로 음성으로 변환하면 이상한 문장이 그대로 나옴
→ 중간에 "스크립트 검수" 노드 추가 필요
```

### n8n 자가복구 시스템
```
러버덕 질문: "AI가 워크플로우를 자동 수정한다면, 잘못 수정하면 어떡하지?"
→ Bounded Autonomy 적용: 모델명 교체 = 자동, 로직 변경 = 승인 필요
→ 수정 전 원본 백업 필수 → 롤백 가능하게
```

### Chatsio (이커머스 최적화)
```
러버덕 질문: "상품 데이터를 어디서 가져오지? 실시간? 캐싱?"
→ 실시간 = API 호출 비용 증가 + 속도 느림
→ 캐싱 = 가격이 변경되면 구버전 표시 위험
→ "30분 캐싱 + 가격 변동 감지 시 즉시 갱신" 전략 결정 필요
```

## 7. 프롬프트 엔지니어링 치트시트

### 위험 신호 감지 키워드
AI 응답에서 다음이 보이면 러버덕 재점검 필요:
- "~할 수 있습니다" (모호한 가능성) → "구체적으로 어떻게?" 재질문
- "일반적으로~" (근거 불명확) → "출처나 데이터는?" 요구
- "간단하게~" (복잡성 축소) → "빠뜨린 예외 케이스는?" 확인

### 응답 형식 앵커링 (Anchor Response)
원하는 출력 형식을 미리 보여주면 일관성 확보:
```
"다음 형식으로 답변해줘:
## 분석 결과
- 문제점: 
- 원인: 
- 해결책: 
- 위험도: (높음/중간/낮음)
- 예상 소요시간: "
```

### 코드 리뷰 요청 시
```
"이 코드에서 다음을 점검해줘:
1. 보안 취약점 (인증, 인젝션, 데이터 노출)
2. 성능 안티패턴 (N+1 쿼리, 불필요한 리렌더링)
3. OST/SRP 위반 여부
4. 에러 핸들링 누락"
```

## 8. 핵심 기억 사항

1. **러버덕 = 질문의 기술이다.** 좋은 질문이 좋은 코드를 만든다.
2. **AI에게 "먼저 질문하게" 하라.** 바로 답변하는 AI는 위험하다.
3. **자율성에는 반드시 한계를 설정하라.** (Bounded Autonomy)
4. **AI 생성물의 45%는 취약할 수 있다.** 인증/결제/보안은 직접 확인.
5. **모호함은 적이다.** 황금공식(배경/결과/제약/형식)으로 모호함을 제거하라.
6. **기록하지 않으면 없는 것이다.** 모든 결정은 PROGRESS.md에 남긴다.
