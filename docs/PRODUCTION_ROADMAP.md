## Phase A: 서비스 런칭 최소 조건 (MVP)

> 목표: 실제 가맹점에 결제 서비스 제공 가능한 최소 상태

### A-1. 실제 VAN/카드사 연동 🔴 필수

**현재**: Mock 카드사 (가짜 승인/거절 시뮬레이션)
**필요**: VAN사와 실제 전문(TCP 소켓) 연동
**비유**: "돈을 주고받는 척만 하는 상태" → 진짜 은행/카드사와 연결

| 단계 | 내용 | 예상 기간 |
|------|------|----------|
| 계약 | VAN사 선정 (NICE/KIS 등) + 계약 체결 | 1~3개월 |
| 규격 분석 | VAN 전문 규격서 분석 + 프로토콜 설계 | 1~2주 |
| 어댑터 개발 | Mock → 실제 VAN 어댑터 패턴 전환 | 2~3주 |
| 인증 테스트 | VAN사 테스트 환경에서 연동 검증 | 2~4주 |
| 운영 전환 | 스테이징 → 프로덕션 전환 | 1주 |

**핵심**: VAN 계약이 가장 오래 걸림 → **가장 먼저 시작해야 함**

---

### A-2. 카드 토큰화 시스템 🔴 필수 (PCI DSS 핵심)

**현재**: 카드번호 직접 처리 로직 없음
**필요**: 카드번호 → 토큰 변환 → 토큰만 저장
**비유**: 고객 카드번호를 "암호화된 별명"으로 바꿔서 저장하는 금고 시스템

| 단계 | 내용 | 예상 기간 |
|------|------|----------|
| 설계 | HSM vs 토큰화 서비스 선택 | 1주 |
| 토큰 저장소 | 토큰-카드번호 매핑 테이블 + 암호화 | 1~2주 |
| 결제 흐름 통합 | 결제 시 토큰 생성 → 승인 시 복호화 | 1~2주 |
| 보안 검증 | 카드번호 평문 노출 없음 확인 | 1주 |

**참고**: 자체 HSM 구축은 비용이 높으므로, 초기에는 VAN사 제공 토큰화 서비스 사용 권장

---

### A-3. 결제창 SDK/iframe 전환 🔴 필수

**현재**: 데모용 직접 입력 폼 (자체 페이지)
**필요**: 가맹점 사이트에 임베드 가능한 SDK/iframe
**비유**: "우리 가게에서만 결제 가능" → "다른 가게에 결제기를 빌려주는" 방식

| 단계 | 내용 | 예상 기간 |
|------|------|----------|
| SDK 설계 | JavaScript SDK API 설계 (checkout.js) | 1주 |
| iframe 구현 | 결제 입력 폼 → 격리된 iframe으로 전환 | 2주 |
| 가맹점 연동 가이드 | SDK 설치/사용 문서 작성 | 1주 |
| 도메인 허용 목록 | 가맹점별 허용 도메인 관리 기능 | 3일 |

---

### A-4. 자동 정산 배치 🟡 중요

**현재**: 정산 계산/조회 API만 존재 (수동)
**필요**: 매일 자동으로 정산 계산 → 검증 → 송금 지시
**비유**: "계산기만 있는 상태" → "매일 자동으로 돈을 나눠주는 시스템"

| 단계 | 내용 | 예상 기간 |
|------|------|----------|
| 스케줄러 | NestJS @Cron 일/주간 정산 배치 | 1주 |
| 정산 엔진 | 거래 집계 → 수수료 차감 → 정산액 계산 | 2주 |
| 은행 API | 실제 송금 API 연동 (오픈뱅킹 등) | 2~3주 |
| 정산 확인 UI | 관리자 정산 승인/반려 화면 | 1주 |
