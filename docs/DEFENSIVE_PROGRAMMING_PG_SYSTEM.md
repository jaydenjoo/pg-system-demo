> **Defensive Programming Blueprint for Payment Gateway System**
> 작성일: 2026.03.07
> 보안등급: 🔴 최고 (돈 + 법적책임)
> 원칙: "결제 시스템은 한 번의 실패가 곧 금전적 손실이다. 모든 경로에서 방어한다."

## 1. 개요

### 1-1. PG System 방어 구조

```
┌──────────────────────────────────────────────────────────────┐
│  Layer 1. 결제창 프론트엔드  → 카드번호 노출 차단 + 입력 방어  │
│  Layer 2. API Gateway 백엔드 → 금액 변조 방지 + 인증/인가     │
│  Layer 3. 에러 처리          → 결제 실패 시 안전한 롤백        │
│  Layer 4. 감사/모니터링      → FDS + 감사 로그 + 실시간 알림   │
│  Layer 5. PG 전용 보안       → PCI DSS + 토큰화 + 정산 검증   │
└──────────────────────────────────────────────────────────────┘
```

> **비유: 은행 금고 시스템**
> - 창구(결제창)에서 1차 신원 확인
> - 금고실 입구(API Gateway)에서 2차 권한 확인 + 금속 탐지기
> - 비상 프로토콜(에러 처리)로 금고 자동 잠금
> - CCTV + 감시 시스템(모니터링)으로 24시간 감시
> - 금고 자체 보안(PG 전용)으로 돈의 이동을 추적

### 1-2. 범용 가이드 vs PG System 차이점

| 항목 | 범용 가이드 | PG System 강화 포인트 |
|------|-----------|---------------------|
| 입력 검증 | 길이/형식 검사 | + 카드번호 Luhn 검증, 금액 3단계 검증 |
| 인증 | JWT/세션 | + PgBasicAuthGuard(가맹점) + MFA(관리자) |
| 에러 처리 | 사용자 친화 메시지 | + 결제 트랜잭션 롤백 + 멱등성 보장 |
| 모니터링 | Sentry/로그 | + FDS(이상거래탐지) + 감사 로그 5년 보관 |
| 데이터 보안 | 암호화 | + 카드 토큰화(PAN 저장 금지) + AES-256-GCM |

## 2. Layer 1: 결제창 프론트엔드 방어

> **목표**: 카드 정보가 가맹점 서버를 거치지 않고 PG로 직접 전송된다
> **핵심**: PCI DSS 6.4.3 — 결제 페이지 스크립트 최소화

### 2-1. 결제 입력 검증 규칙

| 입력 유형 | 검사 규칙 | 에러 메시지 |
|---------|---------|-----------|
| 카드번호 | 16자리 + Luhn 알고리즘 검증 | "유효하지 않은 카드번호입니다" |
| 유효기간 | MM/YY 형식 + 미래 날짜만 | "만료된 카드입니다" |
| CVV | 3~4자리 숫자만 | "보안코드를 확인해주세요" |
| 결제금액 | 양수 + 정수 + 최대 1억 미만 | "결제 금액을 확인해주세요" |
| 주문번호 | 영숫자 + 하이픈, 최대 64자 | "주문번호 형식이 올바르지 않습니다" |
| 가맹점 ID | 존재하는 ID + 활성 상태 | "가맹점 정보를 확인해주세요" |

### 2-2. 결제창 보안 규칙

```
[필수] CSP(Content Security Policy) 적용
  → 인라인 스크립트 금지 (nonce 기반 허용만)
  → 외부 스크립트 화이트리스트만 허용

[필수] 카드번호 마스킹
  → 입력 즉시 앞 6자리 + 뒤 4자리만 표시
  → 전체 번호는 메모리에서만 유지, DOM에 노출 금지

[필수] 제출 후 카드 정보 즉시 파기
  → 토큰화 완료 후 원본 카드번호 메모리에서 제거
  → 브라우저 자동완성 비활성화 (autocomplete="off")

[필수] iframe 격리
  → 결제 입력 폼은 PG 도메인의 iframe 안에서만 렌더링
  → 가맹점 JavaScript가 카드 정보에 접근 불가

[필수] 중복 결제 방지
  → 결제 버튼 클릭 즉시 비활성화
  → 로딩 스피너 표시
  → 응답 수신 후에만 재활성화
```

### 2-3. SDK 입력 방어 패턴 (pg-checkout-sdk)

```
가맹점이 SDK를 통해 결제를 요청할 때:

1. orderId 검증 → 영숫자+하이픈만, 64자 이하
2. amount 검증 → 양의 정수, 100원 이상, 1억 미만
3. orderName 검증 → 1~100자, HTML 태그 제거
4. customerEmail 검증 → 이메일 형식 (선택 필드)
5. redirectUrl 검증 → HTTPS만, 등록된 도메인만
```

## 3. Layer 2: API Gateway 백엔드 방어

> **목표**: "프론트를 절대 믿지 마라" + "가맹점도 믿지 마라"
> **핵심**: 결제 금액 3단계 검증, 모든 요청에 인증/인가

### 3-1. 인증/인가 체계

```
┌─ 가맹점 API ─────────────────────────────────┐
│  PgBasicAuthGuard                             │
│  → secret_key 해시 검증 (bcrypt)              │
│  → IP 화이트리스트 검사                        │
│  → API Key 상태(활성/비활성) 확인              │
│  → Rate Limiting (IP당 분당 10회)              │
└───────────────────────────────────────────────┘

┌─ 관리자 API ──────────────────────────────────┐
│  JwtAuthGuard                                 │
│  → JWT 토큰 검증 (15분 만료)                   │
│  → Refresh Token (7일, HttpOnly 쿠키)          │
│  → Role 기반 접근 제어 (ADMIN/MANAGER/VIEWER)  │
│  → MFA 필수 (PCI DSS 8.4.2)                   │
└───────────────────────────────────────────────┘

┌─ 가맹점/대리점 포탈 API ──────────────────────┐
│  JwtAuthGuard + OwnershipInterceptor          │
│  → merchantId/agentId 격리                    │
│  → 타 가맹점 데이터 접근 차단                   │
│  → 경로: /m/* (가맹점), /a/* (대리점)           │
└───────────────────────────────────────────────┘
```

### 3-2. 결제 금액 3단계 검증 (변조 방지)

```
1단계: 결제 요청 시
  → 가맹점이 보낸 amount와 DB의 주문 금액 비교
  → 불일치 시 즉시 거부 + 감사 로그 기록

2단계: 카드사 승인 응답 시
  → 카드사 응답의 승인 금액과 요청 금액 비교
  → 불일치 시 자동 취소 처리

3단계: 정산 시
  → 정산 금액 = 승인 금액 - 수수료
  → 계산 검증 후 정산 실행
  → 소수점 이하 절사 (원 단위)
```

### 3-3. 서버사이드 검증 체크리스트

```
결제 요청(POST /api/v1/payments):
[필수] orderId 중복 검사 → 멱등성 보장
[필수] amount > 0, 정수, 상한 검사
[필수] 가맹점 상태 = ACTIVE 확인
[필수] 카드 토큰 유효성 검증
[필수] FDS 규칙 엔진 통과 여부
[필수] 요청 본문 크기 제한 (1MB)

결제 취소(POST /api/v1/payments/:id/cancel):
[필수] 원 결제 건 존재 + 취소 가능 상태 확인
[필수] 부분 취소 시 잔여 금액 검증
[필수] 취소 요청자 = 원 결제 가맹점 확인
[필수] 이중 취소 방지 (이미 취소된 건 차단)
```

### 3-4. Rate Limiting 설정

| 엔드포인트 | 제한 기준 | 임계값 | 초과 시 대응 |
|-----------|---------|-------|------------|
| 결제 요청 | 가맹점별 | 분당 60회 | 429 + 감사 로그 |
| 결제 취소 | 가맹점별 | 분당 30회 | 429 + 감사 로그 |
| 로그인 | IP별 | 5회 실패 | 30분 계정 잠금 |
| API Key 발급 | 가맹점별 | 일 5회 | 관리자 문의 안내 |
| 조회 API | 가맹점별 | 분당 120회 | 429 반환 |
| 웹훅 재전송 | 시스템 | 건당 최대 5회 | 수동 확인 안내 |

### 3-5. 데이터베이스 방어

```
[필수] Prisma ORM만 사용 (Raw SQL 금지)
  → SQL Injection 원천 차단

[필수] BigInt 직렬화 처리
  → DB: BigInt ↔ DTO: number 변환 (BigIntSerializationInterceptor)
  → JSON 응답에서 BigInt 직렬화 에러 방지

[필수] 민감 데이터 암호화
  → 카드 토큰: AES-256-GCM 암호화 저장
  → API Secret Key: bcrypt 해시 저장
  → 가맹점 사업자번호: 암호화 저장

[필수] 감사 테이블 삭제 금지
  → audit_logs 테이블: DELETE 권한 제거
  → 5년 보관 의무 (전자금융거래법)

[필수] 트랜잭션 격리
  → 결제/취소/정산: Prisma $transaction으로 원자성 보장
  → 동시 요청 시 낙관적 잠금(Optimistic Locking)
```

## 4. Layer 3: 에러 처리

> **목표**: 결제 실패 시 돈이 빠져나가지 않고, 사용자에게 명확한 안내를 제공한다
> **핵심**: 결제 트랜잭션은 "전부 성공 or 전부 롤백"만 존재한다

### 4-1. 결제 에러 처리 3원칙

```
원칙 1. 돈은 절대 공중에 떠있지 않는다
  → 승인 후 DB 기록 실패 시 → 자동 취소 요청
  → 취소 실패 시 → 수동 확인 대기열에 등록 + 즉시 알림

원칙 2. 에러 메시지에 카드/결제 정보 노출 금지
  → "카드번호 1234-****가 거부되었습니다" ❌
  → "결제가 거부되었습니다. 카드사에 문의해주세요." ✅

원칙 3. 모든 실패는 추적 가능해야 한다
  → 고유 에러 ID 발급 (사용자에게 표시)
  → 에러 ID로 감사 로그 즉시 조회 가능
```

### 4-2. 결제 에러 유형별 대응표

| 에러 상황 | 사용자 메시지 | 시스템 처리 |
|---------|------------|-----------|
| 카드 잔액 부족 | "결제가 거부되었습니다. 카드사에 문의해주세요." | 거부 사유 코드 로그 |
| 카드 유효기간 만료 | "카드 정보를 확인해주세요." | 토큰 무효화 |
| 카드사 응답 타임아웃 | "결제 처리 중 지연이 발생했습니다. 잠시 후 결과를 확인해주세요." | 승인 조회 재시도 → 미확인 시 취소 |
| FDS 거부 | "보안 정책에 의해 결제가 차단되었습니다." | 의심 거래 로그 + 관리자 알림 |
| 가맹점 비활성 | "현재 결제를 처리할 수 없습니다." | 가맹점 상태 알림 |
| 금액 변조 감지 | "결제 요청에 오류가 있습니다." | 즉시 차단 + 보안 알림 |
| 중복 결제 시도 | "이미 처리된 주문입니다." | 기존 결제 결과 반환 (멱등성) |
| 시스템 내부 오류 | "일시적인 오류가 발생했습니다. [에러ID: PG-xxxx]" | 전체 롤백 + 긴급 알림 |

### 4-3. 결제 트랜잭션 롤백 흐름

```
정상 흐름:
  결제 요청 → FDS 검사 → 카드사 승인 → DB 기록 → 웹훅 전송 → 완료

실패 시 롤백:
  1. FDS 거부          → 결제 거부 응답 (롤백 불필요)
  2. 카드사 승인 실패   → 결제 거부 응답 (롤백 불필요)
  3. 카드사 승인 후 DB 실패 → 카드사에 취소 요청 → 취소 실패 시 수동 큐
  4. 웹훅 전송 실패     → 재시도 큐 등록 (결제 자체는 유효)

핵심: 카드사 승인과 DB 기록 사이의 갭이 가장 위험
  → 이 구간에 $transaction 사용 + 실패 시 보상 트랜잭션
```

### 4-4. 웹훅 재시도 전략

```
가맹점 웹훅 전송 실패 시:

재시도 간격: 지수 백오프 (Exponential Backoff)
  1차: 즉시
  2차: 1분 후
  3차: 5분 후
  4차: 30분 후
  5차: 2시간 후 (최종)

5회 모두 실패 시:
  → 상태를 WEBHOOK_FAILED로 변경
  → 관리자에게 알림
  → 가맹점이 수동으로 결과 조회 가능 (조회 API 제공)
```

## 5. Layer 4: 감사 및 모니터링

> **목표**: 금융감독원 요구사항 충족 + 이상거래 실시간 탐지
> **핵심**: 모든 금전 이동을 추적, 5년 보관

### 5-1. FDS (이상거래탐지시스템) 규칙

| 규칙 | 탐지 조건 | 대응 |
|------|---------|------|
| 고액 거래 | 단건 100만원 초과 | 추가 인증 요구 |
| 빈도 이상 | 동일 카드 10분 내 3건 이상 | 차단 + 알림 |
| 시간대 이상 | 새벽 2~5시 거래 | 위험도 점수 가산 |
| 지역 이상 | IP 국가와 카드 발급국 불일치 | 차단 + 알림 |
| 패턴 이상 | 연속 소액(테스트) → 고액 | 차단 + 알림 |
| 실패 반복 | 동일 IP 5분 내 실패 5회 | IP 차단 |

### 5-2. 감사 로그 필수 기록 항목

```
모든 결제 관련 이벤트에 반드시 기록:

[필수] 이벤트 시각 (timestamp, KST + UTC)
[필수] 이벤트 유형 (PAYMENT_REQUEST, APPROVED, CANCELED, SETTLED 등)
[필수] 가맹점 ID + 가맹점명
[필수] 주문번호 (orderId)
[필수] 금액 (amount)
[필수] 결과 (SUCCESS / FAIL / PENDING)
[필수] 실패 시 에러 코드
[필수] 요청 IP 주소
[필수] 처리 소요 시간 (ms)
[필수] 담당자 ID (관리자 작업 시)

기록 금지 (PCI DSS):
[금지] 카드번호 전체 (마스킹 후 앞6뒤4만)
[금지] CVV/CVC
[금지] PIN
[금지] 카드 자기띠 데이터
```

### 5-3. 알림 우선순위

```
🔴 즉시 알림 (5분 내 대응):
  - 결제 시스템 전체 장애
  - FDS 차단 건수 급증 (시간당 10건 이상)
  - 카드사 연동 연속 3회 실패
  - 금액 변조 시도 감지
  - 인증 시스템 연속 실패
  - 미확인 거래 발생 (승인 O, DB 기록 X)

🟡 1시간 내 확인:
  - 웹훅 전송 최종 실패 (5회 재시도 소진)
  - 에러율 3% 초과
  - 응답 시간 5초 초과 지속
  - 정산 금액 불일치 감지

🟢 일간 리포트:
  - 일 거래 건수 / 금액 / 성공률
  - 가맹점별 거래 현황
  - FDS 탐지 건수 요약
  - 시스템 가용성 지표
```

### 5-4. 핵심 KPI

| 지표 | 정상 | 경고 | 위험 |
|------|------|------|------|
| 결제 성공률 | > 98% | 95~98% | < 95% |
| 평균 승인 시간 | < 3초 | 3~5초 | > 5초 |
| 에러율 | < 1% | 1~3% | > 3% |
| FDS 탐지율 | 기록 유지 | 급증 3배 | 급증 5배 |
| 서비스 가용성 | > 99.9% | 99.5~99.9% | < 99.5% |
| 웹훅 성공률 | > 99% | 95~99% | < 95% |
| 정산 정확도 | 100% | — | < 100% (즉시 조사) |

## 6. Layer 5: PG 전용 보안 강화

> **목표**: PCI DSS + 전자금융거래법 + 금융감독원 기준 준수
> **핵심**: 결제 시스템만의 특수 보안 요구사항

### 6-1. 카드 토큰화 (구현 완료)

```
카드번호 처리 흐름:
  1. 결제창에서 카드번호 입력
  2. PG 서버로 직접 전송 (가맹점 서버 미경유)
  3. AES-256-GCM으로 암호화 → 토큰 발급
  4. 가맹점에는 토큰만 전달
  5. 이후 결제는 토큰으로만 처리

절대 저장 금지:
  - 카드번호(PAN) 평문
  - CVV/CVC
  - 카드 자기띠 전체 데이터
  - PIN 번호
```

### 6-2. API Key 보안 (구현 완료)

```
가맹점 인증 키 체계:
  - test_key_xxx: 테스트 환경 전용 (Mock 카드사 연동)
  - live_key_xxx: 운영 환경 전용 (실제 카드사 연동)
  - secret_key: bcrypt 해시 저장 (prefix로 빠른 조회)

키 관리 규칙:
  [필수] Secret Key는 해시만 저장 (원문 복원 불가)
  [필수] 발급 시 1회만 표시, 이후 조회 불가
  [필수] Key 유출 의심 시 즉시 비활성화 + 재발급
  [필수] IP 화이트리스트와 함께 사용
```

### 6-3. 정산 보안 (구현 완료)

```
정산 금액 검증 흐름:
  1. 일별 정산 배치 실행
  2. 승인 금액 합산 vs 개별 건 합산 교차 검증
  3. 수수료 계산 재검증
  4. 불일치 감지 시 정산 보류 + 관리자 알림
  5. 정산 실행 후 결과 감사 로그 기록

정산 방어 규칙:
  [필수] 정산 금액 수동 변경 금지 (시스템 계산만)
  [필수] 정산 실행 전 관리자 승인 (자동 실행 시 이중 검증)
  [필수] 정산 내역 수정 불가 (Append-only)
```

### 6-4. 환경 분리

```
테스트 환경 (test_key):
  → Mock 카드사만 연동
  → 실제 결제 발생 안 함
  → 가맹점 개발 단계에서 사용

운영 환경 (live_key):
  → 실제 VAN/카드사 연동
  → 실 결제 발생
  → 추가 보안 검증 활성화

절대 금지:
  → 운영 데이터를 테스트 환경에 복사
  → 테스트 키로 운영 환경 접근
  → 운영 환경에서 디버그 로그 활성화
```

## 7. 안티패턴 (절대 하지 말 것)

### 7-1. PG 시스템 전용 금지 사항

```
결제 처리:
❌ 프론트엔드에서 받은 금액을 검증 없이 카드사에 전송
❌ 결제 상태를 클라이언트에서 변경 가능하게 설계
❌ 멱등성 키 없이 결제 재시도 허용
❌ 카드사 응답 타임아웃 없이 무한 대기

데이터 보안:
❌ 카드번호를 로그에 평문 기록
❌ API Secret Key를 프론트엔드에 노출
❌ 에러 응답에 DB 쿼리/스택트레이스 포함
❌ 감사 로그 삭제 (법적 의무 위반)

코드 품질:
❌ catch 블록을 비워두기: catch(e) {}
❌ 결제 금액 계산에 부동소수점(float) 사용
❌ any 타입으로 결제 DTO 검증 우회
❌ 트랜잭션 없이 결제 상태 + 잔액 동시 변경
```
