## 1. 왜 PG시스템은 다른가?

### 일반 웹 서비스 vs 결제 시스템

| 구분 | 일반 웹 서비스 | 결제대행시스템 (PG) |
|------|---------------|-------------------|
| **비유** | 동네 카페 | 은행 금고 |
| **데이터** | 이메일, 프로필 | 카드번호, 계좌, 거래내역 |
| **사고 시 결과** | 불편함 | 금전 피해 + 법적 처벌 |
| **보안 수준** | 기본 HTTPS | 다중 암호화 + 토큰화 + 감사 |
| **규제** | 개인정보보호법 | 전자금융거래법 + PCI DSS + 개인정보보호법 |
| **자동화 도구** | n8n, Zapier OK | ❌ 사용 금지 (보안 검증 안 됨) |
| **감사** | 선택 | **필수** (정기 보안 감사) |
| **벌금** | 과태료 수준 | **10년 이하 징역 또는 1억원 이하 벌금** |

### 🚫 PG시스템에서 절대 사용하면 안 되는 것들

| 금지 항목 | 이유 | 비유 |
|-----------|------|------|
| n8n, Zapier, Make | 보안 인증 미비, 데이터 경유지 노출 | 금고 열쇠를 택배로 보내는 것 |
| Supabase (공유 인프라) | 다른 사용자와 DB 서버 공유 | 공용 금고에 내 돈 보관 |
| 무료 호스팅 | 보안 SLA 없음 | 문 없는 창고 |
| 환경변수에 키 하드코딩 | 코드 유출 시 키도 유출 | 금고 비밀번호를 문에 적어놓기 |
| 자동화된 AI 코드 리뷰 없는 배포 | AI 코드 40% 보안 취약 | 안전검사 없이 다리 개통 |

## 2. 반드시 알아야 할 법규와 보안 표준

### 2-1. 한국 법규 (2026년 기준)

#### 전자금융거래법 개정안 (2025.12.16 공포, 2026.12.17 시행)

> 2024년 티메프(위메프·티몬) 미정산 사태를 계기로 대폭 강화되었습니다.

| 항목 | 내용 | 비유 |
|------|------|------|
| **PG업 정의 명확화** | 결제대금 정산에 관여하면 PG업 등록 필수 | 돈을 만지면 반드시 면허 필요 |
| **정산자금 외부관리** | 정산대상금액을 외부에 별도 관리 의무 (1년차 60%→2년차 80%→이후 100%) | 고객 돈을 내 통장이 아닌 별도 금고에 보관 |
| **자본금 요건 강화** | 분기 거래액 300억 초과: 20억 자본금 필요 | 큰 가게 운영하려면 보증금도 커야 함 |
| **행위규칙 신설** | 가맹점과의 계약 정산기한 준수 의무화 | 약속한 날짜에 반드시 정산 |
| **경영지도기준** | 미준수 시 시정조치→영업정지 가능 | 규칙 안 지키면 영업 정지 |
| **벌칙 강화** | 정산자금 유용 시 **10년 이하 징역 또는 1억 이하 벌금** | 고객 돈 횡령은 중범죄 |

#### 전자금융업자의 결제 리스크 관리 가이드라인 (2026.1.5~2027.1.14 시행)

n차 PG 구조(여러 PG가 겹겹이 참여하는 구조)에서의 불법·부실 거래를 규제합니다.

#### 전자금융감독규정

| 규정 | 요구사항 |
|------|---------|
| 제15조 | 전자금융거래 기록 5년 보관 |
| 제17조 | 접근통제 및 내부통제 |
| 제21조 | 정보처리시스템 보호대책 |
| 제32조 | 전자금융사고 보고 의무 |

### 2-2. 국제 표준: PCI DSS 4.0.1 (2025.3.31 전면 시행)

> PCI DSS는 "카드 결제를 다루는 모든 곳이 반드시 지켜야 하는 보안 규칙"입니다.
> 비유: 식당이 식약처 위생 기준을 지켜야 영업할 수 있는 것처럼,
> PG사는 PCI DSS를 지켜야 카드사와 계약할 수 있습니다.

#### PCI DSS 4.0 핵심 12가지 요구사항

| # | 요구사항 | 비유 |
|---|---------|------|
| 1 | 네트워크 방화벽 설치 및 유지 | 건물에 경비실 설치 |
| 2 | 기본 비밀번호 사용 금지 | 자물쇠 초기 비밀번호 변경 |
| 3 | 저장된 카드 데이터 보호 | 금고에 현금 보관 |
| 4 | 전송 중 데이터 암호화 | 현금수송차로 운반 |
| 5 | 악성코드 방지 | 건물에 소독/방역 |
| 6 | 안전한 시스템 개발 및 유지 | 건물 안전 검사 정기 수행 |
| 7 | 업무 필요 기반 접근 제한 | 금고실은 담당자만 출입 |
| 8 | 사용자 식별 및 인증 | 출입증 + 지문인식 |
| 9 | 카드 데이터에 대한 물리적 접근 제한 | CCTV + 잠금장치 |
| 10 | 네트워크 접근 추적 및 모니터링 | 출입 기록 24시간 감시 |
| 11 | 보안 시스템 정기 테스트 | 모의 침입 훈련 |
| 12 | 정보보안 정책 유지 | 보안 규정집 작성 및 교육 |

#### 2025년 4월부터 필수가 된 PCI DSS 4.0 신규 요구사항 (핵심)

| 항목 | 내용 | 비유 |
|------|------|------|
| **MFA 전면 확대** | 카드 데이터 접근하는 **모든** 계정에 다중인증 필수 (관리자만이 아님) | 금고실뿐 아니라 사무실도 이중 잠금 |
| **비밀번호 12자 이상** | 숫자+영문 혼합 12자리 이상 | 자물쇠 복잡도 대폭 상향 |
| **결제 페이지 스크립트 관리** | 결제 페이지의 모든 외부 스크립트 인가·모니터링 필수 | 결제 창구에 아무나 접근 못하게 |
| **자동화된 웹 공격 탐지** | WAF 등 자동 탐지 솔루션 필수 배포 | 자동 감시 카메라 설치 |
| **내부 취약점 스캔** | 인증된 내부 스캔 의무화 | 내부 보안 점검 정례화 |
| **피싱 방어** | DMARC, SPF, DKIM 등 이메일 보안 필수 | 가짜 우편물 차단 |

## 3. 보안 최우선 기술 스택

### 🚨 기존 스택과의 완전한 분리

```
❌ 기존 바이브 코딩 스택 (일반 프로젝트용)
   n8n + Supabase + Next.js 15 (자동화 중심)

✅ PG시스템 보안 스택 (결제 전용)
   전용 서버 + 전용 DB + 전용 프레임워크 (보안 중심)
```

### 추천 보안 스택

| 계층 | 기술 | 이유 | 비유 |
|------|------|------|------|
| **프론트엔드** | Next.js 15 (App Router) + TypeScript | 타입 안전성, CSP 헤더 지원 | 방탄 유리로 만든 창구 |
| **백엔드** | Node.js (Express/Fastify) 또는 NestJS | 구조화된 보안 미들웨어, 의존성 주입 | 보안 경비 시스템 내장 건물 |
| **데이터베이스** | PostgreSQL (전용 서버, 자체 관리) | 전용 인스턴스, 암호화 지원, 감사 로그 | 전용 금고실 (공유 안 함) |
| **암호화** | AES-256-GCM (저장), TLS 1.3 (전송) | PCI DSS 필수 요구사항 | 최고 등급 자물쇠 |
| **토큰화** | 자체 토큰 서버 또는 PG사 SDK | 카드번호를 직접 저장하지 않음 | 진짜 열쇠 대신 임시 출입증 사용 |
| **인증** | JWT + MFA (TOTP) + Session | PCI DSS 4.0 MFA 필수 | 출입증 + 지문 + 비밀번호 |
| **시크릿 관리** | AWS Secrets Manager / HashiCorp Vault | 키를 코드에 넣지 않음 | 열쇠를 별도 금고에 보관 |
| **인프라** | AWS / NHN Cloud (국내) — 전용 VPC | 격리된 네트워크, PCI DSS 인증 | 전용 건물에 입주 |
| **모니터링** | ELK Stack / CloudWatch + 알림 | 실시간 이상 탐지 | 24시간 CCTV + 경비원 |
| **WAF** | AWS WAF / Cloudflare (Enterprise) | 웹 공격 자동 차단 | 건물 진입로 검문소 |
| **CI/CD** | GitHub Actions + 보안 스캔 내장 | 배포 전 자동 보안 검사 | 출고 전 품질 검사 |

### 왜 Supabase/n8n을 쓰면 안 되나? (구체적 이유)

| 도구 | 일반 용도에는 좋지만... | PG시스템에서의 문제 |
|------|----------------------|-------------------|
| **Supabase** | 공유 인프라(멀티테넌트), Row Level Security만으로는 PCI DSS 미충족 | 카드 데이터를 다른 회사와 같은 서버에 저장하는 것 |
| **n8n** | 워크플로우 데이터가 n8n 서버를 경유 | 결제 데이터가 제3자 서버를 거치는 것 |
| **Firebase** | 구글 서버에 결제 데이터 저장, 국내 데이터 주권 이슈 | 외국 은행에 고객 돈을 맡기는 것 |

### 4-2. 핵심 원칙: 네트워크 분리 (Network Segmentation)

> 비유: 은행에서 로비, 사무실, 금고실이 각각 다른 문과 열쇠를 사용하는 것

```
영역 1: DMZ (공개 영역)
  → 웹 서버만 위치
  → 외부에서 접근 가능하지만, 직접 DB 접근 불가

영역 2: Application Zone (내부 영역)
  → API 서버, 정산 서버
  → DMZ에서만 접근 가능, 외부 직접 접근 불가

영역 3: Data Zone (데이터 영역)
  → DB 서버, 토큰 서버
  → Application Zone에서만 접근 가능
  → 가장 강력한 보안 적용

영역 4: Management Zone (관리 영역)
  → 관리자 콘솔, 모니터링
  → VPN + MFA로만 접근 가능
```

### 4-3. 결제 흐름도 (Transaction Flow)

```
고객(카드 소지자)
    │
    ▼
[가맹점 웹사이트] ──→ 결제 요청
    │
    ▼
[PG 결제 페이지] ◀── TLS 1.3 암호화 (HTTPS)
    │
    │ 카드번호 입력
    ▼
[PG API 서버]
    │
    ├─→ ① 카드번호 → 토큰으로 변환 (토큰화)
    │     (원본 카드번호는 즉시 폐기)
    │
    ├─→ ② 사기 탐지 (AI/룰 기반)
    │
    ├─→ ③ 카드사/은행 승인 요청
    │     (VAN사 경유)
    │
    ├─→ ④ 승인 결과 수신
    │
    ├─→ ⑤ 거래 기록 저장 (암호화)
    │
    └─→ ⑥ 가맹점에 결과 응답
         │
         ▼
    [가맹점: 결제 완료 표시]

정산 프로세스 (별도):
    매일/주간 → 거래 집계 → 수수료 차감 → 가맹점 정산금 송금
```

## 5. 보안 12계명 — 코딩 필수 규칙

### 🔐 이 12가지는 결제 시스템 코드에서 절대 어기면 안 되는 규칙입니다

#### 계명 1: 카드번호를 절대 직접 저장하지 마라

```
❌ 잘못된 예:
   DB에 저장: card_number = "4111111111111111"

✅ 올바른 예:
   DB에 저장: card_token = "tok_abc123xyz789"
   (원본 카드번호는 토큰 서버에만 존재)
```

비유: 진짜 열쇠 대신 "출입증"을 발급하는 것. 출입증을 도둑이 훔쳐도 열쇠가 아니라 소용없음.

#### 계명 2: 모든 데이터는 암호화하라 (저장 + 전송)

```
저장 시: AES-256-GCM 암호화
전송 시: TLS 1.3 (HTTPS만 허용, HTTP 완전 차단)

❌ 금지: MD5, SHA1, DES, RC4 (오래된 암호화)
✅ 필수: AES-256, SHA-256 이상, RSA-2048 이상
```

비유: 편지를 보낼 때 반드시 봉투에 넣어 봉인하고 (암호화), 현금수송차로 운반 (TLS)

#### 계명 3: 비밀 키를 코드에 넣지 마라

```
❌ 잘못된 예:
   const API_KEY = "sk-live-abc123...";  // 코드에 직접!

❌ 약간 나은 예:
   const API_KEY = process.env.API_KEY;  // .env 파일

✅ 올바른 예:
   // AWS Secrets Manager에서 런타임에 가져오기
   const secret = await secretsManager.getSecretValue({
     SecretId: 'pg-system/api-keys'
   });
```

비유: 금고 비밀번호를 메모지에 적어 책상에 두면 안 됨. 별도의 보안 금고에 보관해야 함.

#### 계명 4: 입력값을 절대 믿지 마라 (Input Validation)

```
모든 사용자 입력은 "유죄 추정":
  - 결제 금액: 숫자인지, 음수가 아닌지, 합리적 범위인지
  - 카드번호: Luhn 알고리즘으로 유효성 검증
  - 모든 문자열: SQL 인젝션, XSS 패턴 필터링
  - 길이 제한: 필드별 최대 길이 엄격 적용
```

비유: 은행 창구에서 모든 서류를 진위 확인하는 것. "손님이 맞다고 해도" 검증 필수.

#### 계명 5: 에러 메시지에 내부 정보를 노출하지 마라

```
❌ 잘못된 에러:
   "DB 연결 실패: PostgreSQL 15.4 at 192.168.1.100:5432"

✅ 올바른 에러:
   "일시적인 오류가 발생했습니다. 잠시 후 다시 시도해주세요."
   (상세 에러는 내부 로그에만 기록)
```

비유: 금고 비밀번호가 틀렸을 때 "첫 번째 숫자가 틀렸습니다"라고 안내하면 안 됨.

#### 계명 6: 모든 접근을 기록하라 (Audit Logging)

```
기록할 것:
  - 누가 (사용자 ID)
  - 언제 (타임스탬프, KST)
  - 무엇을 (어떤 API, 어떤 데이터)
  - 어디서 (IP 주소, 디바이스)
  - 결과 (성공/실패)

보관 기간: 최소 5년 (전자금융감독규정 제15조)

❌ 금지: 로그에 카드번호/개인정보 포함
✅ 필수: 로그는 별도 서버에 변조 불가능하게 저장
```

비유: 은행의 CCTV. 모든 출입을 녹화하되, 금고 비밀번호가 화면에 찍히면 안 됨.

#### 계명 7: 최소 권한 원칙 (Least Privilege)

```
각 서비스/사용자에게 필요한 최소한의 권한만 부여:

웹 서버: 읽기만 가능, DB 직접 접근 불가
API 서버: 거래 생성/조회만 가능
정산 서버: 정산 데이터만 접근 가능
관리자: 조회는 가능, 수정은 승인 후에만

DB 계정도 분리:
  - app_read: SELECT만 가능
  - app_write: INSERT, UPDATE만 가능
  - app_admin: 스키마 변경 가능 (배포 시에만 사용)
```

비유: 은행에서 경비원이 금고를 열 수 없고, 금고 담당자가 경비 시스템을 건드릴 수 없는 것.

#### 계명 8: 의존성(라이브러리)을 정기 점검하라

```
매주 수행:
  npm audit           (Node.js 취약점 검사)
  npm audit fix       (자동 수정 가능한 것 수정)
  
매월 수행:
  npx npm-check-updates  (구버전 패키지 확인)
  보안 패치 적용
```

비유: 건물의 소방 설비를 정기 점검하는 것. 오래된 설비는 화재 시 작동 안 할 수 있음.

#### 계명 9: 세션과 토큰을 안전하게 관리하라

```
JWT 토큰:
  - 만료 시간: 짧게 (Access: 15분, Refresh: 7일)
  - 서명 알고리즘: RS256 이상 (HS256 지양)
  - Refresh Token: DB에 저장, 1회 사용 후 폐기

세션:
  - 쿠키: HttpOnly, Secure, SameSite=Strict
  - 세션 ID: 암호학적으로 안전한 랜덤 생성
  - 비활성 타임아웃: 15분
```

비유: 출입증에 유효기간을 짧게 설정하고, 분실 시 즉시 무효화하는 것.

#### 계명 10: 결제 금액 변조를 방지하라

```
가맹점에서 보낸 금액과 PG서버의 금액을 반드시 대조:

① 가맹점 → PG: "10,000원 결제 요청" (서명 포함)
② PG 서버: 서명 검증 → 금액 10,000원 확인
③ 카드사 승인 후 → 승인 금액 10,000원 확인
④ ①②③의 금액이 모두 일치하는지 검증

하나라도 다르면 → 거래 거부 + 알림 발송
```

비유: 수표의 금액을 쓴 사람, 받는 사람, 은행이 모두 같은 금액인지 확인하는 것.

#### 계명 11: Rate Limiting (요청 속도 제한)

```
API별 제한:
  - 결제 요청: IP당 분당 10회
  - 로그인 시도: 계정당 5분에 5회 → 초과 시 30분 잠금
  - 카드번호 조회: 계정당 시간당 3회

DDoS 방어:
  - WAF 레벨에서 1차 차단
  - 애플리케이션 레벨에서 2차 차단
```

비유: 은행 창구에서 같은 사람이 10분에 100번 거래를 요청하면 의심하는 것.

#### 계명 12: 배포 전 반드시 보안 검사를 수행하라

```
배포 파이프라인:

코드 작성
  → SAST (정적 분석): 코드 자체의 보안 문제 탐지
  → 의존성 스캔: npm audit
  → 시크릿 스캔: 코드에 비밀 키가 없는지
  → 단위 테스트 + 보안 테스트
  → 코드 리뷰 (보안 관점)
  → 스테이징 배포 → DAST (동적 분석)
  → 수동 보안 테스트
  → 프로덕션 배포
```

비유: 비행기가 이륙 전 반드시 거치는 안전 점검 절차.

## 6. 데이터 보호 3대 핵심 기술

### 6-1. 암호화 (Encryption)

> 비유: 편지 내용을 암호문으로 바꿔서, 열쇠(키)가 있는 사람만 읽을 수 있게 하는 것

| 종류 | 용도 | 알고리즘 | 비유 |
|------|------|---------|------|
| **전송 암호화** | 데이터 이동 시 보호 | TLS 1.3 | 현금수송차 |
| **저장 암호화** | DB에 저장된 데이터 보호 | AES-256-GCM | 금고 잠금장치 |
| **필드 레벨 암호화** | 특정 민감 필드만 추가 암호화 | AES-256 + 별도 키 | 금고 안의 금고 |
| **키 관리** | 암호화 키의 안전한 보관/교체 | KMS (Key Management Service) | 마스터 열쇠 금고 |

#### 키 관리 원칙

```
1. 키는 코드/설정 파일에 절대 포함하지 않음
2. 키는 전용 KMS(키 관리 서비스)에 보관
3. 키는 주기적으로 교체 (90일 권장)
4. 키 접근은 최소 인원만 (분리 보관: 2인 이상 필요)
5. 키 사용 이력은 모두 기록
```

### 6-2. 토큰화 (Tokenization)

> 비유: 진짜 카드번호 대신 "교환권"을 발급하는 것.
> 교환권은 PG 시스템 안에서만 의미가 있고, 밖에서는 아무 가치 없음.

```
원본 카드번호:  4111-1111-1111-1111
        ↓ (토큰화)
토큰:          tok_a8f3e2b1c4d5...
        ↓ (DB에 저장되는 것)
저장값:         tok_a8f3e2b1c4d5...  (원본 카드번호 NO!)

결제 시:
토큰 → 토큰 서버에서 원본 복원 → 카드사 전송 → 즉시 폐기
```

#### 토큰화 방식 선택

| 방식 | 설명 | 장점 | 단점 |
|------|------|------|------|
| **Vault 기반** | 원본-토큰 매핑 테이블 보관 | 단순 구현 | Vault 자체 보안 필요 |
| **Vaultless** | 암호학적 방식으로 토큰 생성 (복원 불가) | 보안 최고 | 구현 복잡 |
| **PG사 SDK** | 토스/나이스 등 기존 PG SDK의 토큰화 | 가장 쉬움 | PG사 의존 |

### 6-3. 데이터 최소화 (Data Minimization)

> 비유: "갖고 있지 않으면 도둑맞을 일도 없다"

```
원칙: 필요하지 않은 데이터는 수집하지도, 저장하지도 않는다.

✅ 저장하는 것:
  - 거래 ID, 토큰, 승인번호, 금액, 시간
  - 가맹점 정보 (사업자번호, 상호명)
  - 카드 마지막 4자리 (표시용)

❌ 저장하지 않는 것:
  - 전체 카드번호 (토큰으로 대체)
  - CVV/CVC (절대 저장 금지 — PCI DSS 명시)
  - 카드 비밀번호
  - 마그네틱 트랙 데이터
```

## 7. 인증과 접근 제어

### 7-1. 다중 인증 (MFA) — PCI DSS 4.0 필수

```
관리자 로그인:
  1단계: 이메일 + 비밀번호 (12자 이상, 영문+숫자)
  2단계: TOTP (Google Authenticator / 기업용 인증 앱)
  3단계: (선택) IP 화이트리스트

가맹점 로그인:
  1단계: 사업자번호 + 비밀번호
  2단계: SMS 인증 또는 인증서

API 접근:
  - API Key + Secret Key (HMAC 서명)
  - IP 화이트리스트
  - 요청별 타임스탬프 + Nonce (재전송 공격 방지)
```

### 7-2. 역할 기반 접근 제어 (RBAC)

```
역할 정의:

[Super Admin] — 시스템 전체 관리 (최소 인원, 2인 이상 승인)
    │
[Settlement Admin] — 정산 관리 (정산 데이터만)
    │
[CS Admin] — 고객 상담 (거래 조회만, 수정 불가)
    │
[Merchant] — 가맹점 (자기 거래만 조회)
    │
[API User] — 연동 시스템 (특정 API만 호출 가능)

원칙:
  - 기본값은 "아무 권한 없음" (Deny by Default)
  - 필요한 권한만 추가로 부여
  - 권한 변경은 로그에 기록
  - 6개월마다 권한 검토 (PCI DSS 요구)
```

## 8. 개발 단계별 보안 체크리스트 (SSDLC)

> SSDLC = Secure Software Development Life Cycle
> "보안을 나중에 추가하는 것이 아니라, 처음부터 함께 만드는 것"

### Phase 1: 요구사항 분석 (보안 요구사항 정의)

- [ ] 처리할 데이터 분류 (공개/내부/비밀/극비)
- [ ] 적용할 법규 목록 작성 (전자금융거래법, PCI DSS, 개인정보보호법)
- [ ] 보안 요구사항 명세서 작성
- [ ] 위협 모델링 수행 (STRIDE 방법론)
- [ ] 데이터 흐름도(DFD) 작성
- [ ] 신뢰 경계(Trust Boundary) 정의

### Phase 2: 설계 (보안 아키텍처)

- [ ] 네트워크 분리(Segmentation) 설계
- [ ] 암호화 전략 수립 (전송/저장/키관리)
- [ ] 인증/인가 체계 설계
- [ ] API 보안 설계 (서명, 제한, 버전관리)
- [ ] 로깅/모니터링 설계
- [ ] 장애 복구(DR) 계획
- [ ] 보안 설계 리뷰 (Architecture Security Review)

### Phase 3: 구현 (보안 코딩)

- [ ] 코딩 표준 문서 준수 (이 가이드의 12계명)
- [ ] TypeScript strict 모드 사용 (any 금지)
- [ ] 입력값 검증 모든 엔드포인트에 적용
- [ ] SQL Parameterized Query 사용 (SQL 인젝션 방지)
- [ ] 시크릿은 KMS/Vault에서만 로드
- [ ] 에러 메시지에 내부 정보 노출 없음
- [ ] CORS 최소한으로 설정
- [ ] CSP(Content Security Policy) 헤더 적용
- [ ] 코드 리뷰 시 보안 체크리스트 사용

### Phase 4: 테스트 (보안 검증)

- [ ] SAST (정적 분석) 수행 — 도구: SonarQube, Semgrep
- [ ] DAST (동적 분석) 수행 — 도구: OWASP ZAP, Burp Suite
- [ ] 의존성 취약점 스캔 — 도구: npm audit, Snyk
- [ ] 시크릿 스캔 — 도구: TruffleHog, GitLeaks
- [ ] 수동 침투 테스트 (전문 업체 위탁 권장)
- [ ] 결제 금액 변조 테스트
- [ ] 인증 우회 테스트
- [ ] 에스컬레이션 테스트 (권한 상승 시도)

### Phase 5: 배포 (안전한 릴리스)

- [ ] 프로덕션 환경 보안 설정 확인
- [ ] TLS 인증서 유효성 확인
- [ ] 기본 비밀번호 모두 변경
- [ ] 불필요한 포트/서비스 비활성화
- [ ] 배포 후 즉시 보안 스캔 재실행
- [ ] 롤백 계획 확인

### Phase 6: 운영 (지속적 보안)

- [ ] 실시간 모니터링 작동 확인

## 10. 운영 및 모니터링

### 10-1. 실시간 모니터링 항목

| 항목 | 임계값 | 알림 방법 |
|------|--------|-----------|

| 에러율 | 1% 초과 | Slack + SMS |
| 로그인 실패 | 5회 연속 | 계정 잠금 + 알림 |
| 비정상 거래 패턴 | AI 룰 기반 | 즉시 알림 + 거래 보류 |
| 서버 CPU/메모리 | 80% 초과 | 알림 + 자동 스케일링 |
| SSL 인증서 만료 | 30일 전 | 이메일 + Slack |
| DB 백업 실패 | 1회 실패 시 | 즉시 알림 |

### 10-2. 사고 대응 절차

```
[LEVEL 1] 탐지 (Detection)
  → 모니터링 시스템이 이상 감지
  → 자동 알림 발송

[LEVEL 2] 분류 (Triage)
  → 심각도 판단 (Low/Medium/High/Critical)
  → 담당자 배정

[LEVEL 3] 대응 (Response)
  → Critical: 서비스 일시 중단 → 원인 분석 → 수정 → 복구
  → High: 해당 기능 차단 → 원인 분석 → 수정
  → Medium: 모니터링 강화 → 다음 배포 시 수정
  → Low: 기록 후 정기 점검 시 수정

[LEVEL 4] 보고 (Report)
  → 전자금융사고 시 금융감독원 보고 (전자금융감독규정 제32조)
  → 사고 보고서 작성 (원인, 영향, 재발 방지책)
  → 고객 통지 (개인정보 유출 시)
```
