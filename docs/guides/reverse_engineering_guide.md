## 다른 사람의 시스템을 분석하고 업그레이드하는 비개발자 방법론

> 
> 맛집 방문(관찰) → 재료 파악(분해) → 조리법 추론(분석) → 내 버전 개발(재설계) → 시식 테스트(검증)

## 1. 역설계란 무엇인가?

### 한 줄 정의
> **완성된 결과물을 거꾸로 추적하여 "왜 이렇게 만들었는지"를 이해하고, 더 나은 버전을 만드는 과정**

### 비유로 이해하기

| 일상 비유 | 역설계 대응 |
|-----------|------------|
| 맛집 음식을 먹고 "이 양념 뭐지?" 추측 | 시스템의 기능을 사용하며 구조 추측 |
| 레시피를 역추적해서 재료 목록 작성 | 사용된 도구/기술/API 목록 작성 |
| "소스에 된장을 넣으면 더 맛있겠다" | "여기에 Claude API를 추가하면 더 좋겠다" |
| 내 버전 레시피로 요리해서 시식 | 새 시스템을 만들어서 테스트 |

### 역설계 vs 그냥 따라하기 (핵심 차이)

| 구분 | 따라하기 (Copy) | 역설계 (Reverse Engineering) |
|------|----------------|------------------------------|
| 목표 | 똑같이 만들기 | **더 좋게** 만들기 |
| 이해도 | 표면만 봄 | 내부 구조까지 파악 |
| 결과물 | 원본의 열화 복사 | 원본을 넘어서는 업그레이드 |
| 리스크 | 원본의 문제도 그대로 복사 | 문제를 발견하고 해결 |

### 비개발자가 역설계를 해야 하는 이유

2025년 연구에 따르면 AI가 생성한 코드의 약 40%에 보안 취약점이 존재합니다. 다른 사람의 시스템을 그대로 가져다 쓰면 그 문제까지 함께 가져오게 됩니다. 역설계를 통해 "왜"를 이해하면, 좋은 부분만 취하고 나쁜 부분은 걸러낼 수 있습니다.

## 2. 6단계 역설계 프로세스

```
┌─────────────────────────────────────────────────────────┐
│                                                         │
│  STEP 1: 정찰 (Reconnaissance)                          │
│  "이 식당이 뭐 파는 집이지?" - 겉모습 파악              │
│     ↓                                                   │
│  STEP 2: 분해 (Decomposition)                           │
│  "주방에 뭐가 있지?" - 부품 목록 만들기                 │
│     ↓                                                   │
│  STEP 3: 흐름 추적 (Flow Tracing)                       │
│  "주문→조리→서빙 순서가 어떻게 되지?" - 데이터 흐름     │
│     ↓                                                   │
│  STEP 4: 약점 분석 (Gap Analysis)                       │
│  "여기 위생 상태가 별로네" - 문제점 발견                │
│     ↓                                                   │
│  STEP 5: 재설계 (Re-Architecture)                       │
│  "내 식당은 이렇게 차려야지" - 업그레이드 설계          │
│     ↓                                                   │
│  STEP 6: 구현 & 검증 (Build & Verify)                   │
│  "시식회 해보자" - 만들고 테스트                        │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

**시간 배분 (바이브 코딩 v2.2 기준)**

| 단계 | 비중 | 소요 시간 (예시) | 담당 |
|------|------|----------------|------|
| STEP 1-2: 정찰+분해 | 20% | 2-4시간 | 사용자 + AI |
| STEP 3: 흐름 추적 | 20% | 2-3시간 | AI (Opus) |
| STEP 4: 약점 분석 | 20% | 2-3시간 | AI (Opus) + 사용자 판단 |
| STEP 5: 재설계 | 30% | 3-5시간 | AI (Opus) → 사용자 승인 |
| STEP 6: 구현+검증 | 10% | 실제 구현 시간 | AI (Sonnet) + 자동 검증 |

## STEP 1: 정찰 - 시스템 겉모습 파악

> **비유: 식당 앞에서 메뉴판 보고, 리뷰 읽고, 외관 살펴보기**

### 1-1. 무엇을 파악해야 하나?

#### A. 시스템의 "정체성" 파악

| 항목 | 질문 | 비유 |
|------|------|------|
| **목적** | 이 시스템은 무슨 문제를 해결하나? | "이 식당은 무슨 요리 전문인가?" |
| **사용자** | 누가 쓰는 시스템인가? | "손님층이 누구인가?" |
| **규모** | 얼마나 큰 시스템인가? | "테이블이 몇 개인 식당인가?" |
| **연식** | 언제 만들어졌나? | "신생 식당인가, 노포인가?" |
| **평판** | 사용자 반응은 어떤가? | "리뷰 별점이 몇 개인가?" |

#### B. 1차 정보 수집 체크리스트

- [ ] 공식 홈페이지/문서 읽기
- [ ] README, CHANGELOG, 릴리즈 노트 확인
- [ ] 유튜브/블로그에서 사용 후기 검색
- [ ] GitHub 있다면 Star 수, Issue 수, 최근 커밋 날짜 확인
- [ ] 경쟁 시스템은 뭐가 있는지 검색
- [ ] 가격 정책/과금 구조 파악

#### C. AI에게 정찰 시키는 프롬프트

```
"[시스템 이름/URL]에 대해 분석해줘.
1. 이 시스템의 핵심 목적이 뭔지
2. 누가 만들었고, 언제부터 존재했는지
3. 주요 기능 5가지
4. 사용자 리뷰에서 가장 많이 언급되는 장단점
5. 비슷한 경쟁 시스템 3개
각각 초등학생도 이해할 수 있게 비유로 설명해줘."
```

### 1-2. 직접 써보기 (체험 정찰)

**가장 중요한 단계!** 아무리 문서를 많이 읽어도 직접 써보는 것만 못합니다.

| 체험 항목 | 구체적 행동 | 기록할 것 |
|-----------|-----------|-----------|
| 회원가입 | 처음부터 가입 과정 전체 | 몇 단계인지, 뭘 요구하는지 |
| 핵심 기능 | 가장 중요한 기능 3개 사용 | 반응 속도, 결과 품질 |
| 에러 상황 | 일부러 잘못된 입력 넣어보기 | 에러 메시지가 어떻게 나오는지 |
| 경계 테스트 | 극단적 입력 (매우 긴 글, 특수문자) | 어디서 깨지는지 |
| UI/UX | 화면 스크린샷 찍기 | 레이아웃, 색상, 흐름 |

## STEP 2: 분해 - 부품 하나하나 뜯어보기

> **비유: 주방에 들어가서 냉장고에 뭐가 있는지, 어떤 조리기구를 쓰는지 파악하기**

### 2-1. 기술 스택 파악하기 (= "재료 목록")

기술 스택은 "이 시스템을 만들 때 뭘 썼는가"입니다. 식당으로 치면 "어떤 재료와 조리도구를 쓰는가"입니다.

#### 기술 스택 파악 방법

| 방법 | 비유 | 구체적 행동 |
|------|------|------------|
| **공식 문서** | 식당 메뉴판에 재료 표시된 것 | README, 기술 블로그 읽기 |
| **브라우저 개발자 도구** | 주방 몰래 들여다보기 | F12 → Network 탭에서 API 호출 관찰 |
| **Wappalyzer** | 식당 영수증 분석 | 크롬 확장프로그램으로 웹사이트 기술 스택 자동 탐지 |
| **BuiltWith.com** | 식당 인테리어 회사 알아내기 | URL 입력하면 사용 기술 목록 표시 |
| **GitHub 탐색** | 레시피 노트 발견 | package.json, requirements.txt 등 의존성 파일 확인 |

#### 기술 스택 분류표 (기록용)

| 계층 | 비유 | 파악할 것 | 예시 |
|------|------|-----------|------|
| **프론트엔드** | 식당 인테리어 (손님이 보는 것) | UI 프레임워크, 스타일링 | Next.js, React, Tailwind |
| **백엔드** | 주방 (손님이 안 보는 것) | 서버, API | Node.js, Python, n8n |
| **데이터베이스** | 냉장고/창고 (재료 보관) | 데이터 저장소 | Supabase, Firebase, MongoDB |
| **AI/ML** | 특급 셰프 (핵심 기술력) | AI 모델, API | Claude API, OpenAI, ElevenLabs |
| **인프라** | 식당 건물 (기반 시설) | 호스팅, 배포 | Vercel, AWS, Elest.io |
| **자동화** | 컨베이어 벨트 (반복 작업 처리) | 워크플로우 도구 | n8n, Zapier, Make |
| **외부 서비스** | 배달 업체, 식자재 납품 | 3rd party API | Stripe, SendGrid, Twilio |

### 2-2. 아키텍처 파악하기 (= "주방 배치도")

아키텍처는 "부품들이 어떻게 연결되어 있는가"입니다. 

```
[사용자가 보는 화면]  ←→  [서버/API]  ←→  [데이터베이스]
    (프론트엔드)           (백엔드)         (저장소)
         ↕                    ↕                ↕
    [CDN/캐시]          [AI 서비스]       [파일 저장소]
```

#### 아키텍처 유형 판별법

| 패턴 | 비유 | 특징 | 판별법 |
|------|------|------|--------|
| **모놀리스** | 1인 식당 (혼자 다 함) | 하나의 앱에 모든 기능 | 서버가 1개, 배포가 한 번에 |
| **마이크로서비스** | 푸드코트 (전문점 모음) | 기능별 독립 서비스 | 여러 API URL, 각각 다른 도메인 |
| **서버리스** | 배달 전문 (가게 없이) | 함수 단위 실행 | Vercel Edge, Supabase Functions |
| **n8n 워크플로우** | 공장 라인 (순서대로) | 노드 기반 연결 | JSON 워크플로우 파일 있음 |

## STEP 3: 흐름 추적 - 데이터가 어디로 흘러가는지

> **비유: "주문서가 손님→홀→주방→조리→서빙까지 어떻게 이동하는지" 추적**

### 3-1. 데이터 흐름도 그리기

이것이 역설계의 **핵심 중의 핵심**입니다. 시스템에서 데이터가 어디서 시작해서 어디로 끝나는지를 추적합니다.

#### 추적할 흐름 유형

| 흐름 유형 | 비유 | 추적 방법 |
|-----------|------|-----------|
| **사용자 흐름** | 손님이 식당에서 걷는 동선 | 화면 전환 순서 기록 (스크린샷) |
| **데이터 흐름** | 주문서가 이동하는 경로 | API 호출 순서 추적 (F12 Network) |
| **돈의 흐름** | 결제→정산 과정 | 과금 구조, API 비용 계산 |
| **에러 흐름** | 문제 발생 시 대응 경로 | 일부러 에러 유발 후 관찰 |

#### 데이터 흐름 기록 템플릿

```
[흐름명: 예) 사용자 질문 → 답변 받기]

① 시작점: 사용자가 채팅창에 질문 입력
   ↓ (데이터: 질문 텍스트 + 세션ID)
② 처리1: 스팸 체크 (3자 미만 거부)
   ↓ (통과하면 다음으로)
③ 처리2: 질문을 벡터(숫자)로 변환 (OpenAI 임베딩)
   ↓ (데이터: 벡터값)
④ 처리3: 유사한 FAQ 검색 (Supabase 벡터 검색)
   ↓ (데이터: 유사도 점수 + FAQ 내용)
⑤ 처리4: AI가 답변 생성 (Claude API)
   ↓ (데이터: 답변 텍스트)
⑥ 끝점: 사용자에게 답변 표시

소요 시간: 약 ___초
비용: 약 ___원/건
실패 지점: ___에서 에러 가능
```

### 3-2. n8n 워크플로우 역설계 방법

n8n 워크플로우는 비개발자에게 가장 읽기 쉬운 형태입니다. 각 노드가 "작업자"이고, 연결선이 "작업 순서"입니다.

#### n8n 워크플로우 분석 체크리스트

- [ ] **트리거**: 워크플로우가 언제 시작되나? (수동/스케줄/웹훅)
- [ ] **노드 목록**: 총 몇 개 노드인지, 각각 뭘 하는지
- [ ] **데이터 변환**: 각 노드에서 데이터가 어떻게 바뀌는지
- [ ] **분기점**: IF/Switch 노드가 어디에 있고, 어떤 조건인지
- [ ] **외부 호출**: 어떤 외부 서비스(API)를 호출하는지
- [ ] **에러 처리**: 에러 발생 시 어떻게 처리하는지
- [ ] **최종 출력**: 마지막에 뭘 내보내는지

#### n8n JSON 읽는 법 (비개발자용)

n8n 워크플로우를 JSON으로 내보내면 이런 구조입니다:

```
비유: JSON은 "레시피 노트"

{
  "name": "내 워크플로우 이름",     ← 레시피 이름
  "nodes": [                        ← 재료/단계 목록
    {
      "name": "Step 1",             ← 이 단계 이름
      "type": "n8n-nodes-base.httpRequest",  ← 어떤 종류의 작업인지
      "parameters": {               ← 세부 설정값
        "url": "https://api.openai.com/v1/embeddings",
        "method": "POST"
      }
    }
  ],
  "connections": {                   ← 단계들의 연결 순서
    "Step 1": {
      "main": [["Step 2"]]          ← Step 1 다음에 Step 2 실행
    }
  }
}
```

**핵심만 보는 법:**
1. `"nodes"` 배열에서 각 노드의 `"name"`과 `"type"` 확인
2. `"connections"`에서 실행 순서 확인
3. `"parameters"`에서 세부 설정 확인 (URL, 메서드 등)

### 3-3. API 호출 추적 방법 (비개발자용)

API는 "점원에게 주문서를 넣는 것"입니다. 어떤 주문서가 오가는지 추적합니다.

#### 브라우저에서 API 추적하기

```
1. 크롬 브라우저에서 분석할 웹사이트 열기
2. F12 (또는 Ctrl+Shift+I) → "Network" 탭 클릭
3. 웹사이트에서 기능 사용하기 (버튼 클릭, 폼 제출 등)
4. Network 탭에 나타나는 요청들을 관찰

관찰할 것:
- URL: 어디로 요청을 보내는지 (= 어느 식당에 주문하는지)
- Method: GET(조회), POST(생성), PUT(수정), DELETE(삭제)
- Status: 200(성공), 400(잘못된 요청), 500(서버 에러)
- Response: 어떤 데이터가 돌아오는지
```

## STEP 5: 재설계 - 업그레이드 설계도 그리기

> **비유: "기존 식당의 좋은 점은 살리고, 부족한 점은 개선한 내 식당 설계도 그리기"**

### 5-1. 업그레이드 전략 3가지

| 전략 | 비유 | 언제 사용 | 장점 | 단점 |
|------|------|-----------|------|------|
| **점진적 개선** | 기존 식당 리모델링 | 원본이 70% 이상 좋을 때 | 빠름, 안전 | 한계 있음 |
| **하이브리드** | 좋은 부분만 가져와서 새로 지음 | 원본이 50% 정도 좋을 때 | 균형적 | 호환성 주의 |
| **완전 재구축** | 새 식당을 처음부터 지음 | 원본이 30% 미만 좋을 때 | 자유도 높음 | 시간 많이 소요 |

### 5-2. 업그레이드 설계 프로세스

```
① 유지 목록 (Keep)
   - 원본에서 잘 작동하는 것들
   - "이건 그대로 가져가자"

② 개선 목록 (Improve)  
   - 원본에 있지만 더 좋게 만들 것들
   - "이건 있는데 부족하니까 업그레이드하자"

③ 추가 목록 (Add)
   - 원본에 없지만 필요한 것들
   - "이건 없으니까 새로 만들자"

④ 제거 목록 (Remove)
   - 원본에 있지만 불필요한 것들
   - "이건 오히려 방해되니까 빼자"
```

### 5-3. 기술 스택 업그레이드 의사결정

기존 시스템의 각 기술을 유지할지 교체할지 판단합니다:

| 판단 기준 | 유지 (Keep) | 교체 (Replace) |
|-----------|-------------|----------------|
| 성능 | 충분히 빠름 | 더 빠른 대안 존재 |
| 비용 | 예산 내 | 더 저렴한 대안 존재 |
| 학습 곡선 | 이미 익숙함 | 새 도구가 훨씬 쉬움 |
| 생태계 | 활발히 업데이트됨 | 더 이상 업데이트 안 됨 |
| 호환성 | 다른 도구와 잘 연동 | 연동이 어려움 |
| 커뮤니티 | 자료/도움 많음 | 정보 찾기 어려움 |

```
- 비개발자가 유지보수 가능해야 함
```

### 템플릿 3: 코드/워크플로우 리뷰 요청

```
배경: 다른 사람이 만든 [n8n 워크플로우/코드]를 검토하려 합니다.

[여기에 코드/워크플로우 JSON 붙여넣기]

분석해줘:
1. 이 코드/워크플로우가 하는 일 (비유로 설명)
2. 좋은 점 3가지
3. 위험한 점 3가지 (특히 보안, 비용)
4. 개선할 점 3가지
5. 내 스택으로 재구현한다면 어떻게 할지

4가지 자기 점검 질문:
- 역할: 각 부분이 하나의 책임만 지는가?
- 흐름: 데이터 흐름이 논리적인가?
- 이유: 왜 이렇게 구현했는지 납득되는가?
- 영향: 한 부분을 바꾸면 다른 곳에 영향이 있는가?
```

### 템플릿 4: 최신 기술로 업그레이드 요청

```
배경: [원본 시스템]이 [날짜]에 만들어졌는데, 
현재 시점(2026년 2월) 최신 기술로 업그레이드하려 합니다.

원본의 핵심 기능: [기능 목록]
원본의 기술 스택: [기술 목록]

요청:
1. 2026년 현재 각 기술의 최신 대안 추천 (비유로 설명)
2. 새로 나온 AI 도구 중 적용 가능한 것
3. 비용 최적화 방안 (같은 기능, 더 싼 비용)
4. 원본에 없지만 2026년에는 필수인 기능
5. 마이그레이션(이사) 계획 (단계별)

제약사항:
- 비개발자가 관리 가능
- n8n 중심 아키텍처
- 월 예산 _____원
```

## 실전 적용 예시

### 예시 1: AI 상담 에이전트 (현재 프로젝트)

다른 PG사의 상담 시스템을 역설계한다면:

```
STEP 1 정찰: 경쟁 PG사 고객센터 실제로 이용해보기
  → 질문 10개 던져보고 답변 품질/속도 기록

STEP 2 분해: 사용하는 기술 추정
  → F12로 API 호출 추적
  → "이 회사는 GPT를 쓰는구나" "이런 FAQ 구조를 가지고 있구나"

STEP 3 흐름: 질문→답변 과정 추적
  → 어디서 사람 연결되는지, 어떤 질문에 잘 못 답하는지

STEP 4 약점: 
  → "수수료 질문에 대답을 안 해주네" (우리는 이원화로 해결!)
  → "3번 이상 못 알아들으면 그냥 멈춰버리네" (우리는 에스컬레이션!)

STEP 5 재설계: 약점을 보완한 우리 시스템 설계
  → 이원화 + 가드레일 5단계 + 벡터 검색

STEP 6 구현: n8n + Claude API + Supabase로 구축
```

### 예시 2: 시니어 롱폼 유튜브 (AutoVox Flow)

인기 있는 시니어 건강 채널을 역설계한다면:

```
STEP 1 정찰: Top 5 채널 구독 후 7일간 시청
  → 업로드 주기, 영상 길이, 조회수 패턴 기록

STEP 2 분해: 각 채널의 제작 파이프라인 추정
  → "이 음성은 ElevenLabs 같다" "이 영상은 InVideo AI로 만든 것 같다"

STEP 3 흐름: 콘텐츠 제작 과정 추적
  → 주제 선정 → 스크립트 → 음성 → 영상 → 편집 → 업로드

STEP 4 약점:
  → "같은 배경 이미지만 반복" → 우리는 다양한 비주얼
  → "자막이 없음" → 우리는 자동 자막 추가
  → "업로드 주기가 불규칙" → 우리는 n8n으로 자동 스케줄링

STEP 5 재설계: 자동화 파이프라인 설계
  → n8n으로 STEP 1~7 연결

STEP 6 구현: 파일럿 영상 3개 제작 후 비교
```

## 흔한 실수와 주의사항

### ❌ 하지 말아야 할 것

| 실수 | 비유 | 왜 위험한지 |
|------|------|------------|
| 원본 코드 그대로 복사 | 남의 레시피 통째로 훔치기 | 저작권 문제 + 원본 버그도 복사 |
| 분석 없이 바로 구현 | 메뉴 안 보고 주문하기 | 시간 낭비, 방향 잘못 잡음 |
| 혼자서 다 하려고 함 | 혼자 10인분 요리하기 | AI에게 분석은 맡기고 판단에 집중 |
| 최신 기술에 눈이 멀림 | 비싼 재료만 사서 예산 초과 | 검증된 도구 우선, 신기술은 포인트만 |
| 보안 검토 생략 | 위생 검사 안 하고 오픈 | 데이터 유출, 비용 폭탄 위험 |

### ✅ 꼭 해야 할 것

| 원칙 | 비유 | 실천 방법 |
|------|------|-----------|
| 먼저 써보고 분석하기 | 먹어보고 평가하기 | 최소 1시간 직접 사용 후 기록 |
| 비유로 이해하기 | 모국어로 번역하기 | 모든 기술 용어를 비유로 정리 |
| 기록하면서 분석하기 | 메모하며 수업 듣기 | 분석 내용을 PROGRESS.md에 기록 |
| AI에게 검증 받기 | 전문가에게 물어보기 | 분석 결과를 AI에게 리뷰 요청 |
| 점진적으로 구현하기 | 한 접시씩 요리하기 | 1~2 기능씩 만들고 테스트 |

### 🔑 Golden Rule

```
"역설계의 목적은 '따라하기'가 아니라 '넘어서기'이다.
원본의 '왜(Why)'를 이해하면, '어떻게(How)'는 AI가 해준다."
```
